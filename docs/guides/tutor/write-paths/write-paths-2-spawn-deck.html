Mental model

The path that starts the conversation

Every other write path in this dashboard answers a question that was already waiting. A Claude Code hook — a script the CLI shells out to at a named moment in a turn — calls this server and then refuses to return, parking the turn on an open HTTP response; your phone reads what the hook registered, you tap, and that tap resolves the held response. Three files do that, on one state machine they share in wait-store.ts: a Map of session id to an entry whose most important field is an injected resolve function, at most one entry per session, and a single settle funnel every exit runs through — plus a reaper, because nothing else will ever come along to release a hold.

spawn.ts inverts all of it. There is no hook, no parked turn, no held response. The dashboard is the one initiating, and what it creates is a detached operating-system process that outlives this server. So every piece of that shared machine is gone: nothing to resolve, nothing to funnel, and — the part worth watching — no reaper either. All the store keeps is the child's handle, so the dashboard can stop the session later.

What replaces them is a different problem. You spawned a detached child in another directory and returned instantly. Did it become a real session? The only honest answer lives on disk, in a transcript this server merely reads. Most of this lesson is about the three seconds before that answer exists.

Section 1 · Untrusted text, meet a flag parser

The prompt is never an argv element

The prompt a user types is the most obviously hostile input this feature handles, and the module's own doc comment states the rule it never breaks:

// spawn.ts:29-34
 *  - The prompt is never an argv element. `claude -p` parses argv the way
 *    almost every CLI does: a value starting with `-`/`--` is read as a flag,
 *    not as data, regardless of what flag it happens to follow. A prompt is
 *    untrusted free text a user typed — `--dangerously-skip-permissions` is a
 *    perfectly ordinary-looking sentence to start a prompt with — so the only
 *    safe place for it is somewhere the CLI's flag parser never looks: stdin.

Read that middle clause carefully: regardless of what flag it happens to follow. Passing the prompt as the value of some flag does not protect it — the parser sees a token that starts with dashes and treats it as the next option, not as the previous one's value.

So the prompt goes somewhere the flag parser never looks. launch writes it to the child's stdin and closes the stream:

// spawn.ts:709-710
  child.stdin?.write(input.prompt);
  child.stdin?.end();

The obvious alternative — append the prompt to argv, quote it carefully — fails because there is nothing to quote against. Quoting is a shell concept, and no shell is involved.

The cost is a stream to manage rather than a string to pass, and a stream is an error surface of its own. Section 3 is where that bill arrives.

Array-form spawn, and never a shell

The second half of the same rule concerns how the child is started at all:

// spawn.ts:37-40
 *  - `child_process.spawn` is always called in array form, never with
 *    `shell: true`. `shell: true` hands the whole command line to `/bin/sh`,
 *    which re-tokenizes it — the exact step that turns a value into code if
 *    it contains a quote, `;`, `$(...)`, or a stray space. Array-form `spawn`

The actual call keeps that promise, and the option that would break it is simply absent:

// spawn.ts:693
    child = doSpawn(config.claudeBin, args, { cwd: ref.path, env, detached: true, stdio: ['pipe', 'ignore', 'pipe'] });

shell: true is genuinely tempting: it is what lets you write cd dir && claude …, expand a ~, or glob a path. Every one of those conveniences is the same mechanism — a second parse of the command line by /bin/sh — and that second parse is exactly what turns data into code.

The trade-off is that everything the shell would have done must now be done in Node explicitly. That is why the working directory arrives as the cwd option rather than a cd, and why the environment is built as an object a few lines earlier instead of being inherited through a shell invocation.

A name that cannot look like a flag

The optional display name is an argv element — it rides in as the value of -n — so it gets a charset of its own:

// spawn.ts:101
const NAME_RE = /^[A-Za-z0-9][A-Za-z0-9 ._-]*$/;

Note that the first character is constrained separately from the rest. The comment above it says why, and it is a bug report rather than a hypothetical:

// spawn.ts:91-96
 *  - **The leading character is constrained separately** so a name can never
 *    itself *look* like a flag: `-p` passed the old charset and became the
 *    value of `-n`. No escalation was possible even then (a name is always
 *    exactly one argv element, pinned by test), but the worst case — a name
 *    the CLI's own option parser chokes on — is not worth keeping for zero
 *    benefit.

The naive position here would be "argv safety already covers it, so skip the charset" — and strictly, for escalation, that is true. The comment concedes as much. The name is sanitized anyway because it also flows into the UI and later onto disk, so it earns validation on its own merits rather than borrowing argv's.

What it costs: a perfectly reasonable name containing /, :, or an emoji is silently dropped to undefined rather than reported. The dot is allowed only because that silence had already eaten v1.2 release once.

A user's prompt begins with the literal text --dangerously-skip-permissions is a flag I should never use. What keeps the CLI from reading that first token as an actual flag?

Nothing rewrites the prompt's content. parseSpawnRequest only trims it and length-caps it (spawn.ts:202-208); the text the child receives is byte-for-byte what the user typed.

There is nothing to quote against. Argv elements are handed to the child directly with no shell in between, so quoting has no meaning at this boundary — and the flag parser would still see the leading dashes.

Correct. launch writes it to child.stdin and ends the stream (spawn.ts:709-710). The CLI's option parser reads argv, never stdin, so no value there can be mistaken for a flag.

Array-form spawn does avoid /bin/sh, and that genuinely matters — but against a different attack. Removing the shell changes nothing about the CLI's own option parser, which would still read a leading -- element as a flag.

Questions you might ask

If array-form spawn never involves a shell, why sanitize the name at all?

Because argv safety is not the only thing the name has to survive. spawn.ts:84-87 makes the reasoning explicit: the name "ends up as a single argv element (never shell-parsed…), but it also flows into UI and, later, onto disk, so it is sanitized on its own merits rather than piggy-backing on argv safety." That last phrase is the point. A charset justified by "the shell can't see it anyway" quietly becomes wrong the first time the value is used somewhere a shell, a path join, or a renderer can see it — and nothing in NAME_RE would have to change for that to break.

Why is . allowed if the charset is meant to be strict?

Because strictness that rejects ordinary names is a bug, not a safety property. spawn.ts:97-99 records both halves: the spec's own charset (/^[\w .\-]*$/) includes the dot, and without it "an ordinary name like v1.2 release was being silently dropped" — silently, because an invalid name fails soft to undefined rather than erroring. The safety argument for excluding it never existed: "a dot is not a path separator, and a name is never joined into a path." Strict where it buys something, permissive where it costs a real user a real name.

buildSpawnArgs pushes input.name twice when remote control is on — is that a bug?

No — the two appearances are different flags' values. -n takes the name as the session's display name (spawn.ts:265), and --remote-control takes its own optional name argument (spawn.ts:269-272):

// spawn.ts:269-272
  if (input.remoteControl) {
    args.push('--remote-control');
    if (input.name) args.push(input.name);
  }

The comment above it says why the same value is reused: without a name the account registration "auto-names itself <hostname>-N", so passing it again is what makes the phone app show the label the form asked for.

Section 2 · Validation

A ladder where malformed means lower

Permission mode is the one field where getting validation wrong is a privilege escalation, so it is not validated — it is clamped:

// spawn.ts:57-117 (compacted here)
/** The permission ladder, lowest to highest. Array index order IS the ordering. */
export const PERMISSION_MODES = ['plan', 'acceptEdits', 'auto', 'bypassPermissions'] as const;
…
export function clampPermission(requested: unknown, ceiling: unknown): PermissionMode {
  return PERMISSION_MODES[Math.min(modeIndex(requested), modeIndex(ceiling))];

The result is never higher on the ladder than the server-configured ceiling, and an unrecognized value on either side — including undefined — resolves to 'auto' rather than to the top. A malformed input can only ever make the outcome less permissive.

Two alternatives are worse in opposite directions. Throwing on an unknown mode turns a client typo into a dead launch button. Defaulting an unknown mode to the top of the ladder turns the same typo into bypassPermissions — the failure you least want to reach by accident.

The accepted cost is real, though: a client sending a mode this server has never heard of gets 'auto' silently, with no error to debug against. And "array index order IS the ordering" means reordering that one array is a semantic change, not a cosmetic one.

Only the prompt refuses on content

Every other field in the request fails soft. An unrecognized model, effort, or name is dropped to undefined; a permissionMode outside the enum is clamped; only the prompt can reject a request for what it says (the next card covers the two fields that refuse on shape):

// spawn.ts:199-213 (compacted here)
  if (typeof b.prompt !== 'string') {
    return { ok: false, error: 'prompt is required' };
  }
  const prompt = b.prompt.trim();
  if (prompt === '') {
    return { ok: false, error: 'prompt must not be empty' };
  }
  if (prompt.length > PROMPT_CAP) {
    return { ok: false, error: `prompt must be at most ${PROMPT_CAP} characters` };
  }
  …
  const model = typeof b.model === 'string' && (MODELS as readonly string[]).includes(b.model)
    ? b.model
    : undefined;

The reason is version skew. The dashboard and this server are deployed together but not always reloaded together, and a phone can hold a stale tab open for days. Strict validation that rejected any unknown field would make every version mismatch a broken launch button; drop-don't-reject means the rest of the request is still honored.

remoteControl shows the same instinct taken to its strictest form — b.remoteControl === true at spawn.ts:222, so absent, "yes" and 1 all fail soft to false.

The cost is silence in the one place you would want noise: a typo'd model name launches happily on the default model, and nothing anywhere says so.

The fields that refuse instead

resume breaks the drop-don't-reject rule on purpose, and the comment states the reasoning as a comparison of harms:

// spawn.ts:225-234 (compacted here)
  // `resume` is the one optional field that REJECTS when present-but-malformed
  // instead of dropping: silently ignoring it would launch a fresh session
  // somewhere the user never asked for, which is worse than any 400. A valid
  …
  if (b.resume !== undefined) {
    if (typeof b.resume !== 'string' || b.resume === '' || !RESUME_ID_RE.test(b.resume)) {
      return { ok: false, error: 'bad resume id' };

That is the whole test for whether a field may fail soft: what does the user get if it is ignored? A dropped model gives them the default model. A dropped resume id gives them a brand new session in a project they were only trying to continue. surface, added with the desktop launch, refuses for the same reason (spawn.ts:178): a headless launch the user believed was going to the desktop app is worse than a 400.

Resume also changes argv's shape, and only its shape:

// spawn.ts:260-262
  const args = input.resume
    ? ['-p', '--resume', input.sessionId, '--permission-mode', input.permissionMode]
    : ['-p', '--session-id', input.sessionId, '--permission-mode', input.permissionMode];

The CLI refuses --resume together with --session-id unless you also pass --fork-session, and forking is precisely what a resume must not do — plain --resume keeps the id and appends to the same transcript, which is what makes the dashboard row wake up. The cost: two argv shapes to keep in step, and no -n or --remote-control on a resume, since those combinations are unverified.

A request arrives with model: "opus-9" and resume: "not a valid id!". What does parseSpawnRequest return?

Dropping is right for model and wrong for resume. Resume is the single optional field that rejects when present-but-malformed (spawn.ts:232-235), exactly so a bad id can never quietly become a fresh session.

Correct. The unknown model fails soft to undefined, but a malformed resume returns { ok: false } and the launch never happens.

An unrecognized model never produces an error at all — it is dropped to undefined (spawn.ts:211-213) so a client running a different build can still launch with the rest of its request honored.

There is no ladder to clamp a session id onto — clamping is what permissionMode gets, because its values are ordered. A resume id either matches RESUME_ID_RE or the entire request is refused.

Questions you might ask

Why does a valid resume force name and remoteControl off?

Because those two combinations were never verified against the CLI. spawn.ts:228-230 states it plainly: "-n renames and --remote-control registration on a resumed session are unverified CLI combos, so they are never sent." The resume branch therefore returns name: undefined, remoteControl: false (spawn.ts:236-241) no matter what the body asked for. Note the shape of the decision: not "these are dangerous", but "we have not measured what they do" — and the fields are dropped rather than the request refused, so the resume the user actually wanted still happens.

remoteControl is checked with === true — why not plain truthiness?

To keep it on the same fail-soft rule as every other optional field. spawn.ts:220-222 spells it out: "Strictly === true: anything else (absent, "yes", 1) fails soft to false, the same drop-don't-reject rule the fields above follow." Truthiness would accept the string "false" and the number 1, quietly turning a malformed body into a session registered with the account. The strict check makes the ambiguous case resolve toward less capability — the same direction clampPermission resolves an unrecognized mode.

Why does parseSpawnRequest ignore body.project entirely?

Because resolving it would make the function impure. spawn.ts:162-164 gives the reason: it "deliberately ignores body.project: resolving a project needs config and the filesystem, which a pure function doesn't have — the handler resolves it separately." That is the seam the whole module is organised around (spawn.ts:5-11 lists the pure core as its own numbered half). Validation you can unit-test with a plain object stays here; anything needing disk lives in the handler.

Section 3 · The launch

Register first, spawn second

The store entry is created before the process is, which looks backwards until you ask where a synchronous failure would otherwise be recorded:

// spawn.ts:667-697 (compacted here)
  entries.set(sessionId, entry);
  …
  let child: ChildProcess;
  try {
    child = doSpawn(config.claudeBin, args, { cwd: ref.path, env, detached: true, stdio: ['pipe', 'ignore', 'pipe'] });
  } catch (err) {
    fail(sessionId, undefined, errMessage(err));
    return sessionId;
  }

A spawner that throws synchronously still has somewhere to write the reason, and the caller still gets an id it can poll for that reason. Spawn-then-register would leave that failure with nowhere to land: the POST returns an id nobody is tracking, and the UI has a row it can never explain.

The stdio triple is deliberate too — stdin piped because the prompt goes there, stdout ignored because nothing reads it, stderr piped because a failure's only explanation arrives on it. And detached: true with child.unref() at spawn.ts:759 is what lets the child outlive this server rather than dying with it.

The trade-off is an entry that can describe a process which never existed. That is why fail tolerates being called on an id that is already gone.

Two environment variables, deleted on purpose

The child inherits this server's environment with two keys removed, and each set back only to a value this server chose:

// spawn.ts:685-689
  const env = { ...process.env };
  delete env.CLAUDE_CODE_ENTRYPOINT;
  if (config.spawnOwnEntrypoint) env.CLAUDE_CODE_ENTRYPOINT = DASHBOARD_ENTRYPOINT;
  delete env.CLAUDE_DASHBOARD_ONESHOT;
  if (input.oneShot) env.CLAUDE_DASHBOARD_ONESHOT = '1';

The first deletion is load-bearing for the dashboard's own display. A server started from inside another Claude Code context — a desktop-app terminal, a Claude-driven shell — carries that marker in its environment, and a child that inherits it stamps claude-desktop into its transcript instead of sdk-cli. The scanner reads that stamp to decide a session's surface, so inheriting the variable costs the launched session its dashboard pill and its right to be resumed. The comment records both readings as measured on CLI 2.1.233, not inferred. The one value set back is the dashboard's own label, and only when SPAWN_OWN_ENTRYPOINT asks for it. CLAUDE_DASHBOARD_ONESHOT goes for the same reason: a server started inside a one-shot session's shell would otherwise turn the reply hold off for every child it spawns.

The tempting shorthand is env.CLAUDE_CODE_ENTRYPOINT = undefined. The comment rejects it precisely: this Node build happens to omit undefined-valued keys, but that is filtering behaviour to not lean on, whereas an absent key needs no guarantee from anyone.

The accepted trade-off is a denylist rather than an allowlist. Everything else the CLI needs — PATH, HOME, credentials — lives in that same environment, so passing only known-good keys would mean maintaining a list of the CLI's entire runtime dependency surface.

Four ways to fail, and the listener that saves the server

Failure can reach the store from four independent places — a synchronous throw from the spawner, the child's own 'error' event, an 'error' on the stdin/stderr streams, and a nonzero 'exit' — and all four route through one function, safe to call twice or after the entry is gone (spawn.ts:609-622).

The third of those is the one worth slowing down for:

// spawn.ts:706-708
  child.stdin?.on('error', err => {
    fail(sessionId, undefined, errMessage(err), child);
  });

A stream is its own EventEmitter. The handler on child does not cover it. Without this listener, an async EPIPE — the child dies, or never reads stdin, before the write finishes — throws unhandled and takes the entire dashboard server down. The comment records that as observed on Node 22, not theorised.

The naive version is one 'error' handler on the child, on the assumption that a parent covers its streams. It reads as complete and is the single most expensive omission available here: the failure mode is not a lost launch, it is a dead server.

The cost is four listeners per launch on a child this process never waits on.

More detail: why 'close' refines rather than replaces

Node may fire 'exit' before the child's stdio has finished draining, so the stderr tail can still grow afterwards. The 'close' handler therefore only refines the message with whatever arrived since. It cannot become the sole path: a spawn that never started at all fires no 'exit' and reaches 'close' with a synthetic negative libuv code, and refining on that would clobber the far better message the 'error' handler already set — which is why the guard at spawn.ts:752 checks all three of tail, non-null code, and positive code.

Why attach an 'error' listener to child.stdin when child already has one?

Nothing retries anywhere in this module. The handler's only action is fail(...) — the launch is recorded as failed, never attempted a second time.

That is a different listener: child.stderr.on('data') accumulates the tail. This one covers an error on the write side, which produces no stderr output at all.

detached governs process groups and lifetime — whether the child survives its parent — and has no bearing on which events reach which emitter. The child's own 'error' event fires exactly as it would otherwise; it simply never covered the stream in the first place.

Correct. child.stdin is a separate EventEmitter, so the child's handler does not cover it — and an async EPIPE with no listener throws unhandled, taking the whole process down.

A launched child exits cleanly with code 0 before any scan has adopted it. What does the store record?

The exit handler returns early on code === 0 (spawn.ts:729), so nothing is ever marked failed. A clean exit is not a failure to report.

Correct. A fast run can finish before the next scan ever sees it, and the transcript, not the exit, is what matters then (spawn.ts:726-728).

The exit handler deletes only a running entry — one a scan already adopted (spawn.ts:725). This one is still launching, so the handler falls through to the clean-exit check and leaves it for a TTL to settle.

That handler guards on code <= 0, so a zero exit is excluded there too — the same clean-exit rule — and it only ever refines a message some earlier failure had already set.

Questions you might ask

Why delete env.CLAUDE_CODE_ENTRYPOINT rather than assigning undefined?

Because the assignment relies on behaviour nobody promised. spawn.ts:679-681 records the measurement and the conclusion together: "this Node build happens to omit undefined-valued keys (measured), but that is filtering behaviour to not lean on — an absent key needs no guarantee at all." An undefined value would work until a Node release passed the key through as the literal string "undefined", at which point the child stamps a bogus entrypoint into its transcript and quietly loses its dashboard pill. delete has no such failure mode to inherit.

stdio is ['pipe', 'ignore', 'pipe'] — why capture stderr but throw stdout away?

Because only one of them tells you something the transcript won't. stderr is kept as a bounded tail (spawn.ts:712-715, capped by STDERR_TAIL_CAP at spawn.ts:477-478) purely so a failed launch can explain itself. stdout of a claude -p run is the session's own output, and the store's charter (spawn.ts:414-417) refuses to duplicate that: "the transcript stays the single source of truth". Piping it would mean buffering a whole session's output in the server's memory to re-derive something already on disk.

All four failure paths call fail — can't two fire and record the failure twice?

They can both fire; there is nothing to corrupt when they do. fail (spawn.ts:609-622) looks the entry up and returns immediately when it is gone — or when it belongs to a newer child that reuses the id — then simply overwrites state, exitCode, error and failedAtMs — assignment, not accumulation. The doc comment at spawn.ts:631-633 makes that a stated property: all four "route through fail, which is safe to call more than once (or after the entry is gone)". The presence guard is what stops a late exit resurrecting an entry that already left the store.

Section 4 · The store

A store defined by what it refuses to be

The store's doc comment opens with a charter, and what it refuses is the part worth reading:

// spawn.ts:409-419
 * RAM-only store of launches still being watched. Charter: explain the first
 * ~3 seconds of a launch, report ones that never became a real session — and,
 * since the Stop control, **hold the live `ChildProcess` handle for as long as
 * the child lives**, so a session this server started can be signalled later.
 *
 * That handle is the whole of the widening, and it is deliberately the *only*
 * widening. This is still NOT a session registry: the transcript stays the
 * single source of truth for what a session is and what it did, the same
 * division `pending.ts`/`plans.ts`/`messages.ts` keep small. What the store now
 * answers is narrower — "do I personally hold a killable handle for this id?" —
 * and it can only ever answer yes for a child this process spawned itself.

That scope is what keeps the dashboard honest about its own architecture. The whole app is a reader of transcripts on disk; a store that remembered live sessions would become a second, competing source of truth, and the two would drift the first time a session ended in a way nobody anticipated.

The alternative a beginner reaches for is exactly that second registry — track every session you launched, because you know about them. It works until a restart, at which point your registry is empty and the sessions are still running, and now the UI disagrees with reality with no way to tell which side is wrong.

The one widening is the child's handle, kept for as long as the child lives so the session can be stopped. Persisting pids instead was refused: a pid recorded before a restart may belong to something else by the time anyone presses Stop, while a handle cannot be stale (spawn.ts:421-427).

The accepted cost is stated plainly in the comment: a restart drops every entry, live children included (spawn.ts:429-431). A launch in flight across a server restart becomes invisible — until the scanner finds its transcript, which is the only claim this design was ever making — and its row has no Stop control.

No reaper, because someone is already looking

Here is the direct contrast with the other three paths, in the code's own words:

// spawn.ts:765-768
 * Expiry is evaluated lazily here rather than on a timer: `pending.ts`/
 * `plans.ts`/`messages.ts` each need a reaper because nothing else would ever
 * read their entries, but the dashboard already polls every 3s, so the next
 * `listLaunching` call is strictly simpler and cannot hold the process open.

Expiry is a side effect of being read. Both TTLs are checked inside the loop that builds the response, and an expired entry is dealt with on the way past:

// spawn.ts:775-792 (compacted here)
  for (const [id, entry] of entries) {
    …
    if (entry.state === 'running') continue;
    if (entry.state === 'launching' && now - entry.startedAtMs > LAUNCH_TTL_MS) {
      …
      if (childAlive(entry.child)) entry.state = 'running';
      else entries.delete(id);
      continue;
    }
    if (entry.state === 'failed' && now - (entry.failedAtMs ?? entry.startedAtMs) > FAIL_TTL_MS) {

A launch past its TTL whose child is still alive is promoted to running rather than dropped: losing the handle would make a live session unstoppable.

A setInterval would work — the three held-response stores share one in wait-store.ts — but it brings machinery this store has no use for: create it on the first entry, clear it on the last, unref it so it cannot hold the process open. All of that exists to serve a reader that never comes, and here a reader comes every three seconds.

The cost is that expiry only happens when someone looks: a store nobody polls holds stale entries for the process's lifetime. Note also that now is a parameter rather than read internally, so a test can simulate elapsed time without faking the clock.

A rail against accidents, not attackers

MAX_LAUNCHING caps in-flight launches at four, and the comment is unusually careful to say what kind of limit it is not:

// spawn.ts:520-527
 *  - **`'launching'` only.** A `failed` entry lingers for `FAIL_TTL_MS`
 *    (5 minutes) purely so the UI can explain itself, and it holds no process
 *    at all — letting it hold a slot would lock a user out of launching for
 *    five minutes after four transient failures, with a 429 that explains
 *    nothing. The rail bounds concurrent *processes*, so it counts them.
 *  - **The pre-adoption window only** (~3s, until `adoptLaunched` sees the id
 *    on disk). It therefore bounds **rapid-fire POSTs**, not the number of live
 *    sessions — ten launches a minute apart all succeed, because each has left

It is not a security boundary, and the comment says why it cannot be: a caller with launch rights can simply prompt one session into spawning more. What it stops is a mistake — a retry loop, a flaky phone connection, a double-tap that beats React's re-render — from becoming four real claude processes on the account's quota. The handler enforces it at api.ts:1175-1176, filtering to 'launching' before answering 429.

Capping live sessions instead would need the session registry the previous card explained this store is deliberately not.

So the honest trade-off: no protection whatsoever against deliberate abuse, and a limit that is invisible to anyone who spaces their launches out — which is the entire population of non-accidents.

You launch ten sessions, one per minute, with MAX_LAUNCHING at 4. How many are refused with a 429?

This is what you would get if the rail counted sessions. It counts entries still in the launching state, and each of those has already left the store long before the next POST arrives a minute later.

The arithmetic is inverted — the first four are the ones that succeed, not the ones refused. And with a full minute between POSTs, no slot is ever occupied when the next one lands.

Correct. The rail bounds only the ~3-second pre-adoption window, so each launch has left the store before the next arrives — it limits rapid-fire POSTs, not live sessions.

A failed entry deliberately holds no slot: it lingers for FAIL_TTL_MS only so the UI can explain itself, and counting it would lock the user out for five minutes (spawn.ts:520-524).

Questions you might ask

Why doesn't a failed entry count toward MAX_LAUNCHING?

Because the rail bounds concurrent processes, and a failed entry holds none. spawn.ts:520-524 works the alternative through: a failed row lingers for FAIL_TTL_MS only so the UI can explain itself, so counting it would "lock a user out of launching for five minutes after four transient failures, with a 429 that explains nothing." The filter is visible at the call site — api.ts:1175 counts only e.state === 'launching'. Four failures in a row is exactly when you most want to retry, which is the worst possible moment to refuse.

Why two TTLs — 60 seconds for a launching entry, five minutes for a failed one?

They answer different questions. LAUNCH_TTL_MS (spawn.ts:486) bounds how long an entry can claim to be starting — roughly "adoption should have happened by now"; past it the entry is promoted if its child lives and dropped if not. FAIL_TTL_MS (spawn.ts:504) bounds how long an explanation stays readable for a phone that isn't looking yet. They are measured from different instants, too: failedAtMs is stored separately "so FAIL_TTL_MS measures time-since-failure, not time-since-launch" (spawn.ts:453).

Why does listLaunching take now as a parameter instead of reading the clock?

So expiry is testable without faking time. spawn.ts:770-771 says it directly: "now is a parameter, not Date.now() read internally, so a test can simulate elapsed time without faking the clock." A test proves the 60-second and 5-minute rules by calling listLaunching(start + 61_000) — no timer, no clock monkey-patching, no waiting. It is the same instinct as the injected resolve in the other three stores: push the untestable dependency out to the caller and the logic left behind is a pure function of its arguments.

Section 4 → Section 5

One question is still open, and it is the one the whole feature turns on: how does a store that refuses to be a session registry ever learn that a launch worked? The answer is that it does not — it is told.

Section 5 · Adoption

The scanner is the witness

The store never looks at the filesystem. The sessions handler, which has just scanned it, hands over the ids it saw:

// api.ts:147-152 (compacted here)
  // Adopt before listing: a launch id that just showed up in `sessions` must
  // not also be reported as still `launching` in the same poll. Attached on
  …
  adoptLaunched(data.sessions.map(s => s.id));
  data.launching = listLaunching();

A launch that became a real session stops being a launch: its id appears in a scan, the entry turns running — off the launching list, but still holding the child's handle for Stop — and from then on the row is an ordinary scanned row like any other. Note the ordering the comment insists on — adopt first, then list, so a single poll can never show the same session twice in two different states.

The alternative is to have launch watch for the transcript itself — an fs.watch, or its own poll. That duplicates the scanner inside the store and gives the store filesystem knowledge its charter says it should not have.

The cost is a dependency on being called correctly: an entry lingers until its TTL if a caller ever passes an incomplete id list.

The witness that proves nothing

Adoption has one exception, and it is the case where the evidence is worthless:

// spawn.ts:816-822
    // A resume entry's id names a transcript that already exists, so seeing it
    // in a scan proves nothing — adopting it here would swallow a failure
    // before the user's next poll could ever render it. Resume entries reach
    // `running` from the other end, via the TTL promotion in `listLaunching`,
    // and otherwise leave through `stopSession` or a failure.
    const entry = entries.get(id);
    if (!entry || entry.resume || entry.state !== 'launching') continue;

For a fresh launch, "this id is on disk" means the CLI got far enough to write a transcript. For a resume, the transcript was there before the launch existed — that is what makes it a resume. So the same observation carries information in one case and none in the other, and the resume flag on the entry exists to tell them apart.

Treating both alike is the natural mistake and it fails silently in the worst direction: the row vanishes on the very first poll, so a resume that died on startup is indistinguishable from one that worked.

The trade-off runs the other way instead. A resume that succeeds sits in the launching list for the full LAUNCH_TTL_MS — sixty seconds — even though it is fine, so the UI briefly shows a launching row for a session that is already running, and the session only becomes stoppable once that TTL promotes it. A stale-looking row is cheaper than a swallowed failure.

Stopping a launch is a deletion, not a state

Stopping goes through stopSession, and for an entry still launching it signals the child and removes the entry in the same breath:

// spawn.ts:858-866
export function stopSession(id: string, now: number = Date.now()): StopResult {
  const entry = entries.get(id);
  if (!entry || !entry.child || entry.state === 'failed') return 'not-found';

  if (entry.state === 'launching') {
    entry.child.kill('SIGTERM');
    entries.delete(id);
    return 'stopped';
  }

Leaving the entry in place would let the eventual exit mark it failed, and it would then sit in the list for five minutes labelled as a crash the user never hit — because they stopped it themselves. The two-state union ('launching' | 'failed') has no way to say "you stopped this" separately from "it broke".

Widening that union to a third state is the obvious fix, and the store does not take it: the public type is a contract the handler and the client already consume, and even the internal running state never crosses into it (spawn.ts:444-450).

The cost is that the entry is gone before the child is: SIGTERM is a request, not a guarantee, and the store has kept no record to correct if the child ignores it. The later exit finds nothing and no-ops through fail's presence guard — the same path any exit takes after a TTL drop. An adopted session is stopped differently: SIGTERM to its process group, a five-second grace, then SIGKILL (spawn.ts:848-852) — and that entry stays until the exit handler drops it, so the row can honestly say stopping.

Why does adoptLaunched skip an entry whose resume flag is set?

It does show up — --resume keeps the id and appends to the same transcript, which is exactly why the scan finds it. Appearing is what makes the check useless here, not what makes it work.

stopSession is one of the three exits available to a resume entry, alongside a TTL and a failure, but it only ever fires when the user asks for it. Nothing about being a resume routes an entry's removal through that function.

Correct. The id was on disk before this launch existed, so seeing it says nothing about whether the run started — and deleting on the first poll would swallow a failure before the user could see it.

The row's id is stable either way — that is why a resume reuses the existing id instead of minting one. What deletion would break is failure reporting, not identity.

Questions you might ask

Why adopt before listing, rather than after building the response?

Otherwise one session appears twice in the same payload. api.ts:147-150 states the ordering as a rule with its reason attached: "Adopt before listing: a launch id that just showed up in sessions must not also be reported as still launching in the same poll."

// api.ts:151-152
  adoptLaunched(data.sessions.map(s => s.id));
  data.launching = listLaunching();

The same call is attached to the error snapshot too, because "a failed scan is exactly when 'did my launch work?' matters most."

After stopSession deletes a launching entry, the child's exit still fires. What happens then?

Nothing — and that is by construction, not luck. The exit handler first asks dropIfRunning, which is false for an id that has left the map, then calls fail, whose first lines look the entry up and return if it is gone (spawn.ts:610-611). One two-line check covers a stop and a TTL drop alike, which is why neither path needs to detach the child's listeners on the way out. The ownedBy check beside it (spawn.ts:617) stops an old child's late exit from failing a newer entry that reuses its id.

stopSession answers not-found for a launch that already failed — why can't you stop it?

There is nothing left to signal. stopSession (spawn.ts:841-843) answers not-found for an "unknown id, a failed entry, or an entry with no child handle", and signals nothing. A failed entry's process is already gone, so the only thing a stop could do is delete a row the UI is deliberately keeping for five minutes to explain itself. The handler turns that into a 404 (api.ts:1360), which is honest: there is no live launch by that id.
