Mental model

The 168 weights are the explanation

Lessons 1 and 2 built a machine that quietly changes a number you act on. The header says the weekly window hits 100% on Thursday afternoon, and that claim now rests on a duty-cycle model learned in the background from a month of samples you never saw.

So the mental model for this lesson is disclosure, not decoration. The Usage tab is not a nicer way to look at a forecast; it is the only thing standing between a wrong projection and being undebuggable. Without it your recourse is opening .usage-profile.json in an editor and counting buckets by hand (UsageProfile.tsx:16-20).

Two panels do that job. A 24×7 heatmap shows all 168 hour-of-week weights at once, so you can see the shape the model believes you work. A forward-walk strip below it replays the specific walk that produced the current projection, climbing to a 100% ceiling, with measured hours drawn solid and assumed ones dashed.

Almost every design decision in these ~925 lines follows from two constraints that sound minor and are not: this is read on a phone, and the dashboard ships five colour themes. Between them they rule out the obvious implementation of the ramp, the tooltip, and the strip.

Section 1 · Why an inspector exists

Disclosure, not decoration

It is worth being precise about what makes this panel load-bearing rather than nice to have, because that judgement is what justifies its size. The forecast changed a number the user acts on, and it did so using a model built from data the user cannot see. A projection that is wrong is therefore not just wrong — it is unfalsifiable from the outside.

The alternative that gets built by default is a confidence label: show thin or ok next to the projection and leave it there. That is strictly cheaper and it answers the wrong question. "How sure is this?" is a summary; "which hours does it think I work?" is the actual thing a user can check against their own memory of last week, and it is the only form of the answer that can be contradicted. A single scalar cannot be contradicted.

So the panel's contract is that the 168 weights are the explanation, shown directly rather than summarised. The confidence label still exists — it sits in the legend — but as one line beside the evidence, not instead of it. The cost is a non-trivial component: 527 lines of view code plus 370 in pure helpers, for a panel most users open once.

The panel could have shipped as a confidence badge next to the projection instead of a 168-cell grid. What does the grid provide that the badge cannot?

The inspector is strictly read-only — it fetches a profile and draws it, and nothing in it feeds back into the forecast. Displaying a model cannot change the model, so accuracy is untouched either way.

A badge is unquestionably the faster read — that is its advantage, and the reason it is the default thing to build. Speed is not what it is missing.

Correct. "Thin" cannot be argued with; "you never work Tuesday mornings" can be, and being wrong about it is visible at a glance. That is what makes the projection debuggable rather than merely qualified.

The endpoint deliberately never carries raw samples — the comment at server/index.ts:152-153 says so. The panel shows the learned weights and per-cell evidence totals, which is derived state, not the sample log.

One fetch, and a length check that is an error

useUsageProfile is 44 lines and does something unusual for this codebase: it fetches once per mount and never polls. Every other view here is on the 3-second refresh, and applying that here would be absurd — a bucket's weight only moves when its ISO week folds, so the data changes on a weekly cadence. Reopening the tab is the refresh.

The guard on the response is the interesting part. A short cells array is treated as an error, not as partial data: 168 exactly, or the hook reports failure and the panel renders "The usage profile could not be read." The permissive alternative — draw whatever cells arrived — produces a torn grid, a week missing its last few hours, with nothing on screen saying so. A visibly broken panel is recoverable; a plausible-looking wrong one is not.

Note the alive flag closed over by both handlers and cleared in the effect's teardown. The tab is lazily loaded and can be unmounted mid-flight, and setting state after that is the classic React warning. Note too that the catch keeps the previous profile rather than clearing it — a failed refetch should not blank a grid the user is reading.

// useUsageProfile.ts:27-41
  useEffect(() => {
    let alive = true;
    fetch('/api/usage/profile')
      .then(res => res.json() as Promise<UsageProfileResponse>)
      .then(profile => {
        // A short cell array would render a torn grid, so treat it as an error
        // rather than drawing part of a week.
        const ok = Array.isArray(profile?.cells) && profile.cells.length === 168;
        if (alive) setState({ profile: ok ? profile : null, loading: false, error: !ok });
      })
      .catch(() => {
        if (alive) setState(prev => ({ profile: prev.profile, loading: false, error: true }));
      });
    return () => { alive = false; };
  }, []);

Its own tab, and why not inside Analytics

UsageView is 28 lines — a title bar and the inspector — and almost all of its interest is in the docstring explaining why it is a separate rail entry rather than a block inside the Analytics tab, which is where a reviewer would naturally suggest putting it.

The dividing line is the subject. Analytics is about sessions: the /kaizen report cards, re-read from transcripts each time you open it. This is about the account. The two share no data, no endpoint and no cadence — one re-reads transcripts on demand, the other reads a profile that moves once a week. Merging them would produce a tab whose two halves refresh on different schedules from different sources and answer unrelated questions, which is a worse outcome than one extra rail entry.

The export default is also load-bearing rather than stylistic: it is what makes this its own lazy chunk, like every section but Sessions. A panel most users open rarely should not be in the initial bundle.

Why does useUsageProfile fetch once per mount rather than joining the dashboard's 3-second poll?

serveUsageProfile reads profileSnapshot(), which is the in-memory live state — the log is not touched. Cost is not the argument; if it were, the fix would be a cache rather than a different cadence.

Correct. Lesson 2's fold is the only thing that moves a weight, and it happens once a week per bucket. Polling every 3 seconds would issue roughly 200,000 requests between two changes.

2 · A calendar, not a bar chart

Section 1 established what the panel owes the user: the weights themselves, not a summary of them.

Section 2 is how 168 numbers get drawn — the five-step ramp and why no colour in it is written down, why "no evidence" is a texture rather than a sixth step, and why a plain table is required rather than optional.

Five steps, plus two states that are not steps

stepOf maps a weight to a CSS class, and the shape of the ladder matters more than the thresholds. Five filled steps cover 0.02 upward, and a weight at or below 0.02 gets the empty string — no step class at all, so the cell renders as a bare bordered track.

That empty case is the design decision. "You never work this hour" and "you work 15% of it" are different statements, and a five-step ramp starting at zero would paint both as q1. A separate third state — untrusted cells, drawn with a hatched unknown texture — completes the set. So the grid has exactly three visually distinct meanings: empty is measured idle, hatched is no evidence, filled is measured active.

The naive version merges the first two: paint an unlearned cell as very pale and be done. It reads as "barely any activity here", which is a claim the model has not made, and it is the single most misleading thing this panel could say — a fresh install would look like a user who never works. The cost of keeping them apart is a legend with three keys instead of one continuous bar.

// UsageProfile.tsx:79-86
function stepOf(weight: number): string {
  if (weight <= 0.02) return '';           // measured idle — the bare track
  if (weight <= 0.2) return 'q1';
  if (weight <= 0.4) return 'q2';
  if (weight <= 0.6) return 'q3';
  if (weight <= 0.8) return 'q4';
  return 'q5';
}

A ramp with no colours in it

The CSS for those five steps names exactly one colour — --cyan, a theme token — and derives the rest by mixing it with the surface at 20, 40, 60 and 80 percent, with q5 being the token itself. Nothing is hard-coded.

Two independent constraints force this. First, a grid of magnitudes is a sequential scale, so a multi-hue ramp is simply the wrong encoding — hue differences read as category differences, and these cells differ only in amount. Second, the dashboard ships five themes as pure token overrides, and this repo forbids a literal colour below the token block: five hand-picked hex values per theme would be 25 values nobody can validate, and the light theme is where such a set breaks first.

The mixing is done in oklab, a perceptually uniform space, which is what makes the five steps read as evenly spaced rather than bunching in the middle the way an sRGB mix does. And because the ramp is a formula over one token, it is monotonic by construction in every theme — a property no hand-picked palette can promise. The hatched unknown state is built the same way, from --hairline and a repeating gradient, so it also cannot go wrong per theme.

// styles.css:786-791

The table is required, not a nicety

A show table toggle swaps the grid for a 24-row, 7-column table of percentages, with an em dash where a cell has no weight. It looks like a courtesy feature. It is an obligation, and the docstring says why in one measurement: the two lowest ramp steps fall below 3:1 contrast against the card surface.

That is below the threshold for non-text contrast, and it is not fixable within the design. Raising the low end of the ramp to clear 3:1 would compress the five steps into a narrower band and cost the panel its main job — telling a 20% hour from a 60% one at a glance. So the ramp keeps its range, and the obligation is discharged by providing a second, non-colour path to the same numbers rather than by weakening the first one.

Note what the table is not: it is not a fallback that appears on small screens or under a media query, and it is not the accessible-only view. It is a toggle any user can flip, rendering from the same cells array, with real <th scope> headers. Every cell also carries an aria-label built from the same tooltip text, with newlines flattened to dashes — so the grid itself is readable without colour too.

More detail — why hours are rows and days are columns

Because the axis needing 24 slots should run the direction a phone actually has. Days across gives 7 columns of 1fr; hours down gives 24 rows that scroll naturally. With aspect-ratio: 1 on the cells, max-width on .up-grid is then the single knob for the whole panel's size: width sets the cell size, which sets the height. The mockup's variant C used 320px, giving 38.84px cells and a 992px-tall week; the shipped version uses 250px, giving ~28px cells and ~730px, which keeps the proportions and brings a week within about one screen.

3 · A tooltip that works on a phone

Section 2 drew 168 cells whose colour carries one number. The evidence behind each — how many weeks, how stale, how far from the trust floor — has nowhere to live in a coloured square.

Section 3 is the floating panel that carries it, and the reasons the obvious implementation is unusable on the device this dashboard is mostly read from.

Why not title

The obvious way to attach per-cell detail is the title attribute: one string, zero code, native everywhere. It shipped that way, and it was wrong for a reason no amount of styling could fix — title never fires on touch. It is drawn by browser chrome, needs a hover dwell, and a phone has no hover. The panel's per-cell evidence was therefore unreachable on the device the dashboard is mostly read from.

The replacement is one real element — a single .up-tip div, reused by every mark rather than one per cell — positioned fixed and faded in on demand. It answers three input modes: hover, press (because pointerenter fires on touch-down, so press-and-hold inspects a cell), and keyboard focus, since every cell is tabIndex={0}.

The trade-off is real and worth naming: a custom tooltip is code you now own — positioning, dismissal, scroll behaviour, and the accessibility affordances the native one gave free. Each of those is a bug you can write. The aria-label on every cell exists partly to cover that: a screen reader reads the same text without going through this panel at all.

textContent, and one shared bundle of handlers

The tooltip text is multi-line — cellTitle and stepTitle both join their lines with \n. Rendering that as markup would mean innerHTML with <br>, and this codebase does not use innerHTML anywhere. So the text goes in via textContent and the newlines are honoured by CSS: white-space: pre-line on .up-tip. Data stays data.

Note also how the panel is updated: tipRef.current is written directly, never through useState. A pointermove that re-rendered 168 cells to move one box would be absurd, and at one event per frame it would be visibly slow. This is the sanctioned exception to "state drives the DOM" — a purely presentational overlay with no bearing on the tree below it.

The handlers come from tipHandlers(text), a factory returning one bundle that is spread onto every mark. It is typed against Element rather than HTMLElement for a concrete reason: the same bundle goes onto the heatmap's <div> cells and the strip's SVG <rect> hit columns, so both halves of the card behave identically.

More detail — what anchorRef is for

It records whether the tooltip was opened by the keyboard, and which mark it belongs to. A scroll normally hides the tooltip, because it is positioned in viewport coordinates and would otherwise hold still while the mark slides out from under it — and the listener is registered with capture because the scroller is an ancestor, not the window. But tabbing to an off-screen cell makes the browser scroll it into view, and hiding on that scroll would blank the tooltip the focus had just opened. So a keyboard-shown tooltip follows its anchor instead of hiding.

Two positioning bugs worth knowing

placeTip is 34 lines for what sounds like "put the box next to the pointer", and both of the surprises in it are the kind that only appear in one configuration.

The first: the panel is position: fixed with no right, so the viewport edge caps its available width. Measured while it happens to be sitting near the right edge, offsetWidth reports a narrower box than it will occupy once moved — and the clamp then lets it hang off screen by the difference. The fix is the two lines that reset left and top to 0 before measuring: always measure from the origin, never from wherever it was last left.

The second is a coordinate-space mismatch. .shell applies zoom: var(--font-scale), so this fixed panel's left/top are multiplied by the text scale, while clientX/Y stay in visual viewport pixels. At 100% the two spaces coincide and the bug is invisible; at 125% the panel lands 25% further down-right than the pointer, an error that grows with position on the page. So the visual coordinates — and the viewport width the clamp compares against — are divided back by that scale.

And one deliberate non-fix. Vertically the panel sits at a constant offset beside the pointer, with no clamp. It used to sit above the mark and clamp to the viewport, but a clamp has an engage point, and crossing it reads as the panel drifting around the pointer mid-sweep: walking down the grid, the tip held still near the top edge and then started moving. Why does the tooltip use textContent plus white-space: pre-line rather than innerHTML with <br>?

Neither property re-renders anything — both write into a ref that React does not manage. What avoids the 168-cell re-render is going through the ref at all instead of through useState, whichever property is used.

Wrapping at max-width works under the default normal too. What pre-line adds is honouring the explicit \n characters, which normal would collapse into spaces.

Screen readers reach this content through each mark's aria-label, not through the tooltip element — and that label flattens the newlines to dashes itself. How the visible panel breaks its lines is not what assistive tech reads.

Questions you might ask

Why one shared tooltip element instead of one per cell?

Because 168 hidden panels is 168 elements, each with its own layout and paint cost, to show at most one at a time — and the strip's hit columns would add ~118 more. One element written by textContent is also what makes the handler bundle reusable across two very different marks. The cost is that the tooltip has no DOM relationship to its mark, which is exactly why anchorRef has to record that relationship by hand for the keyboard case.

Does the tooltip say anything the grid's colour does not?

Yes, and that is its point. A cell's colour carries the weight alone. The tooltip adds the evidence behind it: how many weeks of observation, or how far short of the 60-minute trust floor, plus a staleness note when the hour was last seen more than eight weeks ago. It also states evidence in weeks rather than minutes — "300 min observed" on a one-hour cell reads as a contradiction.

Why does a pointer-shown tooltip hide on scroll while a focused one follows?

Because the pointer does not move with the page. Scrolling slides the cell out from under a panel positioned in viewport coordinates, so the pairing is already broken and hiding is honest. Keyboard focus does move with the page — and browsers scroll a newly focused off-screen cell into view, so hiding there would blank the tooltip that the focus had just opened.

4 · The strip's geometry

Sections 2 and 3 covered the heatmap: what the model believes, hour by hour, and how to interrogate one cell.

Section 4 is the panel below it — the specific forward walk that produced the current projection, drawn as a climb to a 100% ceiling, with every piece of arithmetic pushed out into a testable module.

Cumulative, and clamped at 130

The strip plots one point per walked hour, x being the step index and y the cumulative window percentage after that hour — not the per-hour gain. That is a deliberate reversal of the obvious chart. The panel exists to answer "when does the weekly window hit 100%", and a per-hour bar chart makes the reader integrate 117 bars to find out; a climbing curve puts the answer at an intersection with the ceiling. The per-hour view a bar chart is good at is already served better by the heatmap directly above — the previous strip was competing with its own card.

The y domain is fixed at Y_MAX of 130%, not scaled to the walk's endpoint. Auto-scaling is the reflex and it hurts twice: a walk ending at 294.7% would squash the 100% rule into the bottom third of the box, and two different weeks would render as visibly different charts even where they agree. Since every value over 100% is equally "over", resolving them gains nothing.

yOf is the whole scale, and it is written to hold three properties a fill height and a <polyline> both depend on: non-increasing in cum, never NaN, never outside 0…VIEW_H. Hence the Number.isFinite guard and the clamp before the arithmetic.

// walkChart.ts:97-101
export function yOf(cum: number): number {
  if (!Number.isFinite(cum)) return VIEW_H;
  const clamped = Math.min(Math.max(cum, 0), Y_MAX);
  return VIEW_H - (clamped / Y_MAX) * VIEW_H;
}
More detail — why all the arithmetic left the component

walkChart.ts is 250 lines of pure geometry with no DOM, and the component that draws the strip ends up with none of its own. That split is not tidiness. The previous strip's defects were all geometry — per-element device-pixel rounding, an encoding that contradicted the heatmap, a y value nobody could check — and geometry that only exists inside JSX cannot be pinned by a test. Moving it out is what makes each of those a unit test instead of a screenshot.

One coordinate space, because rounding is per element

The strip is a single <svg> with a viewBox, preserveAspectRatio="none", and vector-effect: non-scaling-stroke on every stroked element. That combination is chosen to remove a specific defect structurally rather than by tuning.

The previous implementation was a flexbox strip of bars. Each bar got a fractional CSS width, and the compositor rounded each bar's two edges to device pixels independently — a ±1px swing between neighbours that no amount of CSS can fix, because the rounding happens per element. Replacing 118 independently rounded boxes with one coordinate space scaled uniformly means there is nothing left to round inconsistently.

The cost is that preserveAspectRatio="none" stretches everything the SVG paints, glyphs included. So no text lives inside it: every label — the 100% ceiling marker, now, the crossing time, the day names — is an HTML overlay positioned by percentage, which is what pctX and pctY are for. The same applies to hit targets: the per-hour hit areas are full-height <rect> columns from hitRect, not a strip along the line, because a 2px-tall target on a curve is a mouse-only affordance.

Splitting the line, and finding the crossing

Measured hours are drawn solid and assumed ones dashed, and the curve's height is identical either way — the forecast genuinely counts an unlearned hour at globalMean, and lesson 2 showed why that pessimism is deliberate. Only the ink says which hours are a measurement. With no learned buckets at all the whole line is dashed, which is the honest picture.

A single <polyline> cannot be half dashed, which is the entire reason splitRuns exists: it cuts the walk into consecutive runs of equal learned. The subtlety is the boundary — each run includes the first point of the next run, so the solid and dashed segments meet instead of leaving a one-hour hole at every transition. That is what Math.min(i, walk.length - 1) is doing.

crossingX then locates where the curve reaches 100%, interpolating inside the crossing hour from cum and gain — never from a parsed timestamp — using the same arithmetic the server used for exhaustAt, so the drawn rule cannot drift away from the label printed beside it. Two guards earn their keep: a first point already at the ceiling has no segment to its left to interpolate along, and a zero-gain hour cannot be the hour that crossed — which is also what stops the division by zero.

// walkChart.ts:115-130
export function splitRuns(walk: ForecastStep[]): WalkRun[] {
  if (walk.length === 0) return [];
  const pts = walkPoints(walk);
  const runs: WalkRun[] = [];
  let start = 0;
  for (let i = 1; i <= walk.length; i++) {
    if (i === walk.length || walk[i].learned !== walk[start].learned) {
      // `i` is one past the run; including its point (when there is one) is the
      // shared boundary that closes the gap.
      const end = Math.min(i, walk.length - 1);
      runs.push({ learned: walk[start].learned, points: pts.slice(start, end + 1) });
      start = i;
    }
  }
  return runs;
}

In splitRuns, why does each run include the first point of the run that follows it?

The final run already ends on the last point: the loop's i === walk.length arm fires there, and Math.min caps end at the last index. The right edge is covered without any overlap.

Dash phase is not preserved across separate <polyline> elements and nothing here tries to — each run's dashes restart. The shared point solves a geometry problem, not a stroke-pattern one.

Correct. Runs are drawn as separate polylines because one cannot be half dashed, and without a shared boundary point each transition would show a visible hole in the curve.

crossingX reads the raw walk array directly and never sees a run — it interpolates from that hour's own cum and gain. The two functions share no data at all.

dayTicks emits a tick when the local date changes, rather than when a step's local hour reads 00:00. What does that buy?

A calendar date does not repeat inside a seven-day walk, and the tick count is the same either way in the normal case — one per day. The difference only shows up on the abnormal day.

Correct. Slices are cut with a single UTC offset held for the whole window, so after a transition a slice's local hour drifts by one and a midnight can be missed or seen twice.

getDay() is perfectly reliable at midnight — it is read on the same Date either way, and the labels come from it in both designs. The problem is whether the tick fires at all, not what it is called.

The now tick is pushed unconditionally before the loop starts, so it is present under either rule. It is also the reason the loop begins at i = 1.

Questions you might ask

Why does the strip's tooltip distinguish "assumed" from "measured" when the weights can be identical?

Because that is the only place the distinction can be stated. A fallback weight of 1.0 and a measured weight of 1.0 are the same number and completely different claims, and the curve's height is identical for both by design. stepTitle therefore says assumed (no evidence) or measured, N weeks on its last line — the strip's dashing shows it graphically, and the tooltip states it in words for anyone who cannot resolve dash from solid.

What happens when there is no walk to draw?

The section stays mounted and says why, in one sentence from absentText. Its three cases map to the response's walkAbsent reason: recording off (no profile to project through), no current burn rate (nothing to project from), or no weekly window read yet. Unmounting instead was rejected deliberately — idle is a normal state, and a panel that vanishes reads as a broken feature rather than as nothing to show.

5 · Not a blank grid

Everything so far assumed there is a profile to draw. On a fresh install there is not — and will not be for a week.

Section 5 is the last piece: the status line that tells an early user which of two gates they are waiting on, so the first week does not read as a broken feature.

168 identical hatched cells is the correct first week

Here is the problem the 76 lines of pure helper exist for. A weight is a weekly EWMA fold, so there is genuinely nothing to average until a week completes. For the whole first week, every one of the 168 cells is untrusted, so the grid is entirely texture — correct by the model, and indistinguishable from a feature that does not work.

profileProgress counts what there is to count: buckets with any evidence at all, total observed minutes, buckets past the trust floor, and buckets actually carrying a weight. Four numbers rather than one, because two independent gates stand between a recorded minute and a coloured cell — 60 lifetime observed minutes for that bucket, and at least one fold. An hour can be past the floor and still have no weight for up to a week, so a single "progress" number could not say which one you are waiting on.

Note that TRUST_FLOOR_MIN is redeclared here, client-side, rather than sent over the wire. It is a constant of the model, not a runtime value — but the duplication is real, and the docstring says outright that the two must move together.

// usageProfile.ts:45-54
export function profileProgress(cells: UsageProfileCell[]): ProfileProgress {
  let touched = 0, totalMin = 0, atFloor = 0, trusted = 0;
  for (const c of cells) {
    if (c.observedMin > 0) touched++;
    totalMin += c.observedMin;
    if (c.observedMin >= TRUST_FLOOR_MIN) atFloor++;
    if (c.weight != null) trusted++;
  }
  return { touched, totalMin, atFloor, trusted };
}

Naming the gate, and naming the date

RecordingStatus turns those four counts into one of three messages, and the branch order is the useful part. If any bucket carries a weight, say how many — the panel is working, nothing to explain. Otherwise, if some buckets have cleared the floor, the thing being waited on is the fold, so name the date it will happen. Otherwise nothing has cleared the floor yet, so name the floor itself and the date.

Naming a date is what makes this a status line rather than a spinner. "Weights appear when the week rolls over on Mon 1 Sep" is checkable; "collecting data…" is not. nextWeekStartMs computes it: local midnight starting the next ISO week. Note the two details in seven lines — getDay() || 7 converts JavaScript's Sunday-is-0 to ISO's Sunday-is-7, and on a Monday the function deliberately returns the following Monday, because the current week is the one still accumulating.

One early-return sits above all of it: with recording off and nothing observed, the component renders nothing, because the separate .up-off block already explains the situation and offers the setting to change it. Two overlapping explanations of the same emptiness would be worse than one.

// usageProfile.ts:63-69
export function nextWeekStartMs(nowMs: number): number {
  const d = new Date(nowMs);
  d.setHours(0, 0, 0, 0);
  const isoDay = d.getDay() || 7;   // getDay(): Sunday is 0; ISO wants 7
  d.setDate(d.getDate() + (8 - isoDay));
  return d.getTime();
}
More detail — the third branch's wording

The "no weights yet" branch names both gates in one sentence, because at that point the user is waiting on both and will hit them in order. Its text reads: an hour needs TRUST_FLOOR_MIN minutes of evidence, and the first fold happens when the week rolls over on that date. The interpolated constant is the same 60 the server enforces, which is the practical reason the duplication matters — the sentence would otherwise be able to state a threshold the server does not use.

Recording has been on for three days. Several hour-of-week buckets have well over 60 observed minutes, but no cell is coloured. What does the status line say, and is anything wrong?

The trusted count counts buckets whose weight is non-null, and no fold has happened yet, so it is zero. The grid and the count agree with each other; there is nothing stale to reload.

It is reachable — a bucket accrues at most 60 minutes a week, and an hour observed edge to edge clears the floor in a single week. And the recording-off message comes from the .up-off block, which reads the setting, not any count.

The early return is much narrower than that: it fires only when recording is off and touched is zero. With evidence recorded, this is precisely the case the status line was written for.

Correct: this is the middle branch. The trust floor is cleared, the fold is not, and a fold only happens when a sample lands in a bucket in a new ISO week. The line names that Monday so the wait is legible.

Questions you might ask

Why does profileProgress compare against observedMin when lesson 2's server-side gate used lifetimeObservedMin?

Because they are not the same field. The endpoint shapes each bucket into a UsageProfileCell, and that cell's observedMin is the evidence total the panel is meant to show — which is why cellTitle can print "N of 60 min needed" from it. The server's own trust gate still runs on its internal lifetime counter; the client is reading a shaped response, not the raw bucket.

Why is Date.now() called inside the component rather than passed in?

Because the value it feeds — the next ISO week's start — is a display string, not part of any computation the rest of the panel depends on, and it is re-derived on each render anyway. The arithmetic that would be awkward to test with an ambient clock lives in nextWeekStartMs, which takes nowMs as a parameter and is unit-tested with fixed inputs. The component keeps only the call.
