Mental model

A sleeping laptop is the best teacher

Lesson 1 ended with the weekly forecast walking forward across 168 hour-of-week weights, and treated those weights as given. This lesson is where they come from.

The useful mental model is not a logger. It is a witness taking pairwise depositions. The recorder never observes "activity" — it cannot. All it ever gets is the same odometer reading lesson 1 described: a utilization percentage and a reset stamp, once a minute. So it works on pairs: take this sample and the one before it, and ask what the span between them proves.

The surprise is which pairs carry the most information. Two readings seven hours apart, both saying 61.0%, both naming the same reset — a laptop asleep overnight — are not a hole in the data. Utilization is cumulative inside a window, so identical readings prove nothing was spent between them. That is a measurement of seven idle hours, and night is exactly what the profile most needs to learn (usage-history.ts:13-19).

Everything else follows from that stream of verdicts: file each one under the hour of the week it happened in, fold a week's worth into a standing weight once the week ends, and let an hour that has gone quiet fade rather than freeze.

Section 1 · What a pair of samples proves

Four verdicts, from two readings

classifyInterval is the whole sensor. Given two consecutive samples it returns one of four kinds — active, idle, ambiguous or reset — and the rest of the module only ever consumes that verdict, never the raw readings.

Read the body in order, because it is a priority ladder. A different reset stamp means the two readings measure different windows, so the span is meaningless: reset. A utilization that went down by more than MOVE_EPSILON (0.5) means the window rolled between the samples even though the stamp did not look like it: also reset. A rise means real spend, so active — unless the pair is too far apart to say when in the span it happened, which is ambiguous. Everything left over is flat, and flat is idle.

The naive alternative is a boolean — "busy or not" — derived from whether utilization moved. That collapses two genuinely different failures into one: "I know this hour was quiet" and "I have no idea what happened in these six hours" would both come back as not busy, and the second would then be learned as evidence of idleness. Four kinds exist so the two discardable cases can be discarded separately from the two that teach.

// usage-history.ts:158-164

The duration test is real, but it is only reached inside the delta > MOVE_EPSILON branch — it guards a rise that cannot be pinned to a particular hour. This pair does not rise at all, so control never enters that branch and the duration is never consulted.

reset is decided only by evidence that the window itself changed: a resetsAt outside the two-minute slack, or a utilization that fell. Here the stamp matches and the number held, so both of those tests pass. Sampling gaps get no say.

Correct. Utilization is cumulative within a window, so two equal readings under one reset stamp are positive evidence of no spend. The comment on the final line calls it exactly that — the sleep measurement.

active requires delta to exceed MOVE_EPSILON. A flat reading gives delta of zero, which falls through to the last line.

Same window? Not string equality

The first line of the ladder asks whether two samples describe the same window, and the obvious implementation — compare the two resetsAt strings — is wrong in a way that would silently kill the feature.

The upstream endpoint recomputes that stamp per request, so four consecutive real fetches of one unchanged 5-hour window came back with sub-second jitter, around 0.85s across the set. String equality would therefore report a different window on almost every tick: every interval would classify as reset, every interval would be discarded, and the profile would never learn a single minute. The same jitter would also make shouldWrite append a log line every tick.

sameWindow parses both stamps and allows SAME_WINDOW_MS (two minutes) of slack — chosen with room on both sides, three orders of magnitude above the measured jitter and three orders below the smallest genuine window change (+5h, or +7d). Note the two guards around the comparison: null against a string is treated as a real change, since a scoped and an unscoped window are not the same thing, and an unparseable stamp falls back to strict equality rather than pretending to a numeric answer.

// usage-history.ts:84-91
function sameWindow(a: string | null, b: string | null): boolean {
  if (a === b) return true;
  if (a === null || b === null) return false; // scoped ⇄ unscoped is a real change
  const ta = Date.parse(a);
  const tb = Date.parse(b);
  if (Number.isNaN(ta) || Number.isNaN(tb)) return a === b;
  return Math.abs(ta - tb) <= SAME_WINDOW_MS;
}
More detail — why the tolerance is a constant and not a heuristic

Two minutes is not tuned to the jitter; it is chosen to sit in the empty space between two known scales. Anything the endpoint's own recomputation can produce is under a second. Anything a real window transition can produce is at least five hours. A threshold anywhere in the middle behaves identically, which is what makes the constant safe to hard-code rather than something that needs to adapt. The docstring at usage-history.ts:69-81 records the four observed stamps so the next reader does not have to re-measure them.

Ambiguity is duration, not direction

The counter-intuitive half of the ladder is the active branch's duration test. A rise is only usable if it can be attributed to a particular hour, and MAX_ATTRIBUTABLE_MS (five minutes) is where that stops being possible. Two samples a minute apart with utilization rising pin that spend to that minute — and this is the only way activeMin ever grows. A rise across six hours could have happened in any of them.

The tempting alternative is to spread a long rise across the hours it spans, weighted by what the profile already believes about those hours. That is quietly circular: the profile would be training on its own output, and an early wrong guess would reinforce itself every time a long interval landed on it. Discarding is the honest option — you lose the datum instead of manufacturing one.

Note which way round the asymmetry runs, because it was gotten backwards once. It is rises that expire with duration, never flats. A flat interval is idle at any length, because flatness across six hours says the same unambiguous thing about all six. Invert this — make long flats ambiguous and long rises idle — and every hour learns as idle, which is the shape of a profile that looks plausible and is wrong everywhere.

// usage-history.ts:58-64

Two samples are 45 seconds apart. Utilization rose from 58.0 to 61.0. Their resetsAt stamps differ by 0.85 seconds. Which kind comes back?

This is exactly the bug sameWindow exists to prevent, and it is worth being able to predict its consequences: with string equality this pair — and nearly every other pair — would classify as reset, so nothing would ever be learned. 0.85s is well inside the two-minute slack, so the window counts as unchanged.

Correct. Same window within the slack, a rise of 3.0 well past MOVE_EPSILON, and 45 seconds is inside the five-minute attributability limit — so the spend is pinned to that minute.

ambiguous has one and only one cause: a rise spanning more than MAX_ATTRIBUTABLE_MS. The stamps play no part in it — by the time that branch runs, sameWindow has already said yes.

The threshold for "a move" is MOVE_EPSILON, which is 0.5. A rise of 3.0 is six times that, so the flat fall-through is never reached.

Questions you might ask

Why is a utilization drop treated as a reset rather than as bad data?

Because within one window utilization only ever rises. A fall therefore means the window rolled between the two samples, and the new window's stamp had not been observed yet — the drop is the earlier, more reliable signal of the roll than the stamp is. MOVE_EPSILON keeps rounding noise from tripping it. Lesson 1 met the same constant in recordAndPace, doing the same job for the pace ring; the comment at usage-history.ts:67 says so explicitly.

Does classifyInterval ever look at the clock, e.g. to ignore intervals while the machine was suspended?

No — it reads only t, utilization and resetsAt off the two samples, and duration only inside the rising branch. It has no notion of suspend, and deliberately so: a suspended machine is indistinguishable from an awake, idle one as far as the account is concerned, and the account is what is being forecast. Both spend nothing, and both should teach the same thing.

Where does the maxAttributableMs parameter get overridden?

Only by tests. The signature at usage-history.ts:153-157 gives it a default of MAX_ATTRIBUTABLE_MS, and every production call site — the classifier ring inside recordTick, and accumulate's first line — passes two samples and nothing else. It is a seam for pinning the branch, not a knob.

2 · Two calendars, one grid

You have a verdict about a span of time. Now it has to be filed — and the span rarely lines up with the boxes it is filed into.

Section 1 turned a pair of readings into one of four kinds. Section 2 is about the two independent calendars that decide where a kind lands: the Sunday-first index of the 168 buckets, and the Monday-anchored ISO week that groups folds.

168 buckets, indexed from Sunday

A bucket is one hour of the week: Monday 09:00 is a different bucket from Tuesday 09:00, and there are 168 of them. hourOfWeek, which lesson 1 met on the forecast side, is the index function both halves share — the walk queries the same numbering the recorder writes.

It counts from Sunday, and that choice is purely mechanical: getUTCDay() already numbers Sunday as 0, so shifting a timestamp into local time and reading the day and hour off it is a two-line function. A Monday-first index would need a wrap-around adjustment on every call, for no gain — the index is internal, and nothing outside these two modules ever sees a bucket number.

Note the shape of the local-time trick: rather than reasoning about time zones, the offset in minutes is added to the timestamp and the result is read with UTC accessors. That keeps one arithmetic path for every zone. The cost is the one lesson 1 already flagged for the walk — a single offset held for a whole window, so a DST transition inside it is off by an hour.

// usage-forecast.ts:100-109
 * Sunday-first matches `Date.prototype.getUTCDay()`'s numbering, which is what
 * makes this a three-line function instead of a wrap-around puzzle: shift the
 * timestamp into local time and read the UTC day and hour off it. (ISO weeks
 * start on Monday, and `usage-history.ts` folds on that boundary — bucket
 * indexing and fold grouping are independent axes. Keep them straight.)
 */
export function hourOfWeek(ms: number, offsetMinutes: number): number {
  const local = new Date(ms + offsetMinutes * 60_000);
  return local.getUTCDay() * 24 + local.getUTCHours();
}

…and folded on Monday

The second calendar is the one that decides when a week is over, and it is not the same axis. isoWeekKey returns a YYYY-Www string for the real ISO-8601 week — Thursday-anchored numbering, Monday start.

Only equality is ever compared between two of these keys, which makes the obvious shortcut tempting: dayOfYear / 7 produces a string that also changes about once a week and needs none of the Thursday arithmetic. The reason it is not used is that a wrong boundary does not produce a wrong number, it produces a wrong count of folds: an off-by-one at the year edge either folds a bucket twice in one week — halving a weight for no reason — or skips a fold entirely, leaving a week's accumulators to be merged into the next week's.

So the two axes are independent by design, and the warning is written into both files: buckets are indexed Sunday-first, folds are grouped Monday-first. Nothing reconciles them, and nothing needs to — an index and a grouping key are different questions about the same timestamp. Conflating them is the trap, and the excerpt above from usage-forecast.ts exists to flag it from the other side.

// usage-history.ts:175-181
export function isoWeekKey(ms: number, offsetMinutes: number): string {
  const d = new Date(ms + offsetMinutes * 60_000);
  // Move to the Thursday of this ISO week; its calendar year is the ISO year.
  const dayNum = (d.getUTCDay() + 6) % 7; // Monday = 0
  const thursday = new Date(d.getTime());
  thursday.setUTCDate(d.getUTCDate() - dayNum + 3);
  thursday.setUTCHours(0, 0, 0, 0);

One interval, sliced at every hour boundary

A classified interval is a span, and buckets are hours, so accumulate walks the span and cuts it at each local hour boundary. Each slice credits its own bucket with its own minutes: observedMin and lifetimeObservedMin always, plus activeMin when the kind is active. Only active and idle get this far — reset and ambiguous return the state untouched.

The load-bearing detail is line 248: weekKey is recomputed per slice, from that slice's own start. Computing it once per interval would be the natural simplification, and it breaks precisely at the boundary that matters — an interval spanning Sunday 23:30 to Monday 00:30 would file its Sunday minutes under the new ISO week, so the Sunday bucket's pending accumulators would be stamped a week ahead and fold at the wrong time.

Note also that accumulate copies before it mutates: the buckets array is mapped into fresh objects and observedWeeks is spread. Callers hold onto earlier states, so in-place mutation would rewrite history under them. The cost is an 168-element copy per sample, once a minute — irrelevant next to the class of bug it removes.

3 · Fold, then age

Section 2 filed minutes into buckets, but nothing has produced a weight yet — only pending counters for the current week.

Section 3 is the once-a-week event that turns those counters into a standing weight, and the decay that keeps an abandoned hour from holding its weight forever.

A week's ratio, folded through an EWMA

A bucket accumulates observedMin and activeMin for the current week and carries no weight at all until that week ends. The trigger is not a timer: foldBucket runs at the top of every slice in accumulate, and does nothing unless the slice's week key differs from the bucket's stamp. So the fold happens on the first sample that lands in a bucket in a new week — lazily, per bucket, with no scheduler.

The fold itself is an exponentially weighted moving average with EWMA_ALPHA of 0.3: three tenths of the new week's ratio replaces seven tenths of the standing weight. That gives a half-life of about two weeks — fast enough to follow a genuine change of working habit, slow enough that one unusual week does not rewrite the profile. A plain lifetime average would be the simpler choice and would never adapt; taking the newest week outright would make the forecast jitter weekly.

Two guards on the way in. A bucket whose stamp is null has never been touched, so there is nothing to fold; and a bucket with no pending minutes folds nothing and — the part that matters for the next card — decays nothing.

// usage-history.ts:207-218
function foldBucket(bucket: Bucket, weekKey: string, observedWeeks: string[]): void {
  if (bucket.weekStamp === null || bucket.weekStamp === weekKey) return;
  if (bucket.observedMin <= 0) return; // nothing pending: nothing folds, nothing decays

  const ratio = bucket.activeMin / bucket.observedMin;
  const folded = bucket.weight === null
    ? ratio
    : (1 - EWMA_ALPHA) * bucket.weight + EWMA_ALPHA * ratio;
  const k = skippedWeeks(observedWeeks, bucket.weekStamp, weekKey);
  bucket.weight = folded * Math.pow(1 - EWMA_ALPHA, k);
  bucket.observedMin = 0;
  bucket.activeMin = 0;

Decay after the fold, never before

Look again at the order of the last four statements: fold into folded, then multiply by (1 - EWMA_ALPHA)^k, then clear the accumulators. That order is load-bearing, and reversing it is the kind of change that looks like a harmless reshuffle.

The reason is what the two operations are about. The pending accumulators belong to the week named by bucket.weekStamp, and the skipped weeks came after that week. So they age that week's contribution: fold first, and the decay applies to a value the skipped weeks postdate, which is correct. Decay first, and you age a weight that those weeks predate — and worse, a first-ever fold (where bucket.weight is null) would have nothing to decay, so the decay would be skipped entirely and a stale seed would enter at full strength.

The alternative design is a scheduled sweep: once a week, walk all 168 buckets and decay the untouched ones. That needs a timer, needs to know it did not miss a week while the process was down, and gives a bucket two places it can change. Folding lazily on first touch keeps every mutation of a bucket in one function, at the cost of this ordering subtlety — which is why the docstring above the function spells it out.

// usage-history.ts:191-195
function skippedWeeks(observedWeeks: string[], from: string, to: string): number {
  let n = 0;
  for (const wk of observedWeeks) if (wk > from && wk < to) n++;
  return n;
}

Weeks we were recording, not weeks that elapsed

skippedWeeks does not count calendar weeks between two stamps — it counts entries of observedWeeks strictly between them. That list holds every ISO week in which any bucket was observed at all, which makes it a record of when the recorder was running.

The distinction is the whole point. Two months of server downtime should age nothing: an hour you have no evidence about did not become less likely, you simply stopped looking. Two months of ordinary use during which that hour was always quiet should age it, at the normal half-life. Counting elapsed weeks would conflate the two and quietly wash out a profile every time the dashboard sat unused — the naive version of "old data decays".

The list is appended to inside the same slice loop, kept sorted, and pruned to the newest MAX_OBSERVED_WEEKS (26 — half a year). Sorting matters because the comparison is a string range: ISO keys are YYYY-Www, zero-padded precisely so that lexical order is chronological order. The pruning bounds the file and the loop; 26 weeks of decay already drives any weight to a rounding error.

More detail — why a quiet bucket cannot simply be left alone

Because a weight only moves when its bucket folds, and a bucket only folds when a sample lands in it in a new week. An hour you have stopped working would therefore keep its old weight indefinitely, while lifetimeObservedMin — which never resets — kept it above the trust floor. The forecast would go on projecting spend into an hour abandoned months ago, with full confidence. The module docstring at usage-history.ts:28-32 states the rule as "a quiet bucket must decay, not freeze".

Suppose foldBucket were rewritten to apply the decay before the EWMA fold. What is the specific extra failure on a bucket's first-ever fold?

The two assignments that zero observedMin and activeMin are unconditional and run once either way. Reordering the fold and the decay does not duplicate them.

The first fold is precisely where the extra failure lives. Every later fold at least has a weight to decay, so reordering there only ages the wrong quantity; the first fold has no weight at all.

That is what counting elapsed weeks would do, and it is the behaviour observedWeeks exists to avoid. Those eight weeks are absent from the list, so skippedWeeks does not see them and k does not include them.

Correct. The weight survives untouched, because "we have no evidence" is not the same claim as "we observed this hour going quiet". Decay resumes at the normal rate once ordinary use records weeks again.

Questions you might ask

A bucket can only gather 60 minutes a week. Does an observedMin of 12 make its ratio nearly worthless?

The ratio itself is fine — 12 observed minutes of which 6 were active is a real 50%. What makes it thin is the sample size, and that is the trust floor's job, not the fold's: foldBucket will happily fold a 12-minute week, but deriveProfile will not expose the resulting weight until the bucket has 60 lifetime observed minutes. Section 4 covers that gate. The two mechanisms are deliberately separate.

Why keep observedWeeks globally instead of per bucket?

Because the question it answers is global: "were we recording that week at all?" A per-bucket list would answer "was this hour observed that week", which is the wrong question — an hour being unobserved in a week we were otherwise recording is exactly the case that should decay. One shared list also costs 26 strings instead of 168 lists, and is what makes a skipped week mean the same thing to every bucket.

4 · Trust before use

Section 3 produced weights. Not all of them deserve to be believed.

Section 4 is the gate between a folded weight and a weight the forecast is allowed to walk over, and the deliberately pessimistic fallback for everything on the wrong side of it.

A lifetime floor, not a weekly one

deriveProfile is the boundary between this module and the walk lesson 1 taught. It maps the 168 buckets into the DutyProfile the forecast consumes, and it is where the trust decision is made: a bucket's weight is passed through only if its lifetimeObservedMin is at least TRUST_FLOOR_MIN. Everything else becomes null — no weight, rather than a low one.

The floor is on lifetime minutes, and this is the third thing in this module that was gotten backwards once. A bucket is one hour of the week, so it can gather at most 60 minutes per week: a per-week floor of 60 could only ever be met by an hour observed edge to edge, every single week, and any lower per-week floor would be satisfied by a fortnight of noise. Trust has to accrue across weeks. Recency is not this gate's job at all — that is what the decay in section 3 tracks, and the two are intentionally different mechanisms with different inputs.

Notice which counter is which: observedMin is cleared on every fold, lifetimeObservedMin never is. That is the only reason the floor can be stated as a lifetime quantity at all.

// usage-history.ts:55-56
/** Lifetime observed minutes before a bucket's weight is used at all. */
export const TRUST_FLOOR_MIN = 60;

The fallback is 1, and that is on purpose

Untrusted buckets need something to stand in for them, and deriveProfile supplies globalMean: the mean of the weights that are trusted. An hour with no evidence is treated as an average hour, which is the least-assuming answer available once some hours are known.

The interesting case is a brand-new profile, where nothing is trusted and there is no mean to take. The value is 1 — assume every unknown hour is fully active. That is deliberately pessimistic, and the reasoning is about what it degrades to: a duty cycle of 1 for every hour makes the forward walk arithmetically identical to lesson 1's flat-rate projection. So a fresh install behaves exactly as it did before this feature existed, and improves from there. Picking an optimistic default instead — say 0.3, "most hours are quiet" — would invent a claim from no evidence and push the projected exhaustion later, in the direction that costs a user their week.

trustedCount travels alongside as the confidence input: the walk reports none, thin or ok from it, so the UI can say how much of the projection rests on measurement.

// usage-history.ts:277-287
export function deriveProfile(state: ProfileState): DutyProfile {
  const weights: (number | null)[] = state.buckets.map((b) =>
    b.lifetimeObservedMin >= TRUST_FLOOR_MIN ? b.weight : null
  );
  const trusted = weights.filter((w): w is number => typeof w === 'number');
  return {
    weights,
    globalMean: trusted.length > 0 ? trusted.reduce((a, w) => a + w, 0) / trusted.length : 1,
    trustedCount: trusted.length
  };
}

Why is TRUST_FLOOR_MIN checked against lifetimeObservedMin rather than against the current week's observedMin?

Backwards: observedMin is the counter that accumulates during the week and is zeroed by the fold. It is non-zero most of the time. The problem with it is its ceiling, not its timing.

Correct. One hour of the week comes round once a week, so a weekly floor at 60 would demand a perfectly, continuously observed hour every week. Trust accrues across weeks; recency is the decay's job instead.

That is what decay does, and it works on the weight rather than on trust. lifetimeObservedMin never decreases, so a bucket that has cleared the floor stays cleared — an abandoned hour keeps its trust and loses its magnitude.

The reset kind causes an interval to be discarded before accumulate touches any bucket — it never clears a counter. The only thing that zeroes observedMin is a fold.

5 · The I/O shell and the opt-in

Sections 1 to 4 were pure functions: samples in, a DutyProfile out, nothing touched.

Section 5 is the shell around them — two files on disk, the write policy, the single entry point that owns a tick, and the setting without which none of it runs.

Two files, and only one of them is authoritative

Recording writes two gitignored files at the repo root. .usage-history.jsonl is an append-only log of raw samples — one compact JSON object per line, replayable, rotated, and explicitly not authoritative. .usage-profile.json is the learned state, written atomically via a temp file and a rename, and it is the profile's source of truth.

The tempting simplification is one file: keep the log and rebuild the profile from it on startup. It fails for a specific, non-obvious reason. The log is deliberately sparse — write-on-change plus a heartbeat — while learning happens at the full one-minute cadence against the in-memory previous sample. A flat stretch that ends in a rise gets written to the log as one long rising interval, which classifies as ambiguous and is discarded. Replaying the log would therefore throw away exactly the evidence live sampling captured. The log is for charts and for rehydrating the pace ring; the profile file holds the learning.

The cost of two files is that they can disagree, and the design accepts it: the log is allowed to be lossy, and rotation throws its oldest half away without the forecast noticing — which is the same fact from the other side.

// usage-history.ts:296-306
/** Append-only raw samples. Replayable, rotated, never authoritative. */

/** The learned profile — derived state, written atomically, authoritative. */

/** Longest silence before an unchanged sample is written anyway. */
export const HEARTBEAT_MS = 900_000;
/** ~32 MB, roughly two years of write-on-change samples. */
export const MAX_HISTORY_BYTES = 33_554_432;
/** Tail window for a read — the same 256 KB `transcript.ts` uses. */
export const TAIL_BYTES = 262_144;
More detail — rotation, tail reads, and the 32 MB ceiling

rotateIfNeeded trims the log to its newest half once it passes MAX_HISTORY_BYTES (33,554,432 bytes — 32 MiB, roughly two years of write-on-change samples), by reading that half back and rewriting the file. readRecentSamples reads only the trailing TAIL_BYTES (262,144 — 256 KiB, the same window transcript.ts uses) and drops the first line whenever the window did not reach the top of the file, since a byte-offset read almost always starts mid-line. Malformed lines are skipped individually rather than failing the whole read.

Write on change, plus a heartbeat

shouldWrite is the log's whole policy, and it is four lines of guards. No previous sample writes. A utilization that moved by more than 0.01 writes. A different window writes — via the same sameWindow from section 1, which is why the reset-stamp jitter would otherwise have appended a line every tick. Otherwise, write only if the last write was at least HEARTBEAT_MS ago: 15 minutes.

Sampling every minute into the log would be the obvious approach and buys the profile nothing, because the gap rule from section 1 already reads sparse records correctly — two flat samples 15 minutes apart say the same thing as fifteen consecutive flat ones. What the heartbeat adds is a distinction the log could not otherwise express: it is a liveness marker. A gap longer than the heartbeat means the recorder was not running, which is what separates server downtime from a quiet machine — the same distinction observedWeeks makes for decay.

The trade-off is that the log's timestamps are irregular, so anything charting it has to handle uneven spacing rather than assuming a fixed cadence.

// usage-history.ts:346-355
export function shouldWrite(
  prev: UsageSample | null,
  next: UsageSample,
  heartbeatMs: number = HEARTBEAT_MS
): boolean {
  if (prev === null) return true;
  if (Math.abs(next.utilization - prev.utilization) > 0.01) return true;
  if (!sameWindow(prev.resetsAt, next.resetsAt)) return true;
  return next.t - prev.t >= heartbeatMs;
}

Where the files live, and why not cwd

Both paths are resolved through repoRoot, which walks up from this module's own directory looking for a package.json. It deliberately does not use process.cwd(), even though settings.ts next door does.

The asymmetry is about the cost of being wrong. A settings file that resets when you start the server from a different directory is an annoyance you notice immediately. A history file that does the same thing is weeks of learning silently replaced by an empty one, with no error and nothing in the UI to say so — you would only find out when the forecast quietly went back to flat-rate. So the two files use different strategies on purpose.

Note the failure mode of the walk itself: it stops when path.dirname stops changing, and falls back to process.cwd() at the filesystem root rather than throwing. An unreadable directory is caught and the walk continues. This is the same rule the repo's guide tooling follows — walk up for a marker, never a fixed ../.. hop count, because a fixed count silently repoints the moment a file moves.

// usage-history.ts:317-329
export function repoRoot(startDir: string = import.meta.dirname): string {
  let dir = startDir;
  for (;;) {
    try {
      if (fs.existsSync(path.join(dir, 'package.json'))) return dir;
    } catch {
      /* unreadable — keep walking */
    }
    const parent = path.dirname(dir);
    if (parent === dir) return process.cwd(); // hit the filesystem root
    dir = parent;
  }
}

One tick, and the switch that arms it

recordTick owns everything that happens per sample: append if shouldWrite says so, push the classified interval onto a 12-hour RAM-only ring, fold the interval into the live state via accumulate, and save every HEARTBEAT_MS. The whole body sits in a try that swallows — recording must never be able to break the usage fetch it rides along with.

One line inside is worth pausing on: accumulate is called with localOffsetMinutes(sample.t), never 0. The profile has to be learned on the same local clock the walk queries it with; passing 0 would shift every bucket by the UTC offset, producing a profile that is internally consistent and describes someone else's day.

None of this runs by default. recordUsageHistory is a persisted setting, default false, and startUsageRecording re-reads it on every tick rather than capturing it once — so toggling the switch in Settings takes effect immediately, with no restart. The recorder also needs its own interval, because sampling is otherwise request-driven: /api/sessions is the only caller of the usage refresh, so with no browser open nothing would be sampled and the recorded history would describe when the dashboard was watched rather than when work happened.

Questions you might ask

Why is refresh passed into startUsageRecording instead of imported?

To break an import cycle. usage.ts imports this module for recordTick, so this module importing usage.ts back for getCachedUsageState would be circular. Injection also keeps one code path to Anthropic: production passes the same non-blocking refresh the /api/sessions poll uses, rather than a second fetcher with its own cache and its own failure modes.

What is the 12-hour ring for, if the profile is already being folded?

It answers a different question: how much active time was actually observed inside a given span, which lesson 1's active-rate correction divides by. observedActiveMs returns null rather than a partial sum when the ring does not cover the whole span — a half-covered lookback would undercount active time, and since the caller divides by it, the rate would come out too high in the pessimistic direction, silently. Twelve hours is twice the weekly lookback.

Why is the profile saved only every 15 minutes rather than every tick?

Because a lost save costs at most that window's folds, while writing 168 buckets to disk every minute is pure churn. The save is also the trigger for rotateIfNeeded, so the two disk-touching operations share one cadence. The write itself is atomic — temp file then rename — and returns false instead of throwing, mirroring how settings.ts reports a failed persist.
