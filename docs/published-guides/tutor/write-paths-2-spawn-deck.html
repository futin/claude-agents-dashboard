Mental model

The path that starts the conversation

Every other write path in this dashboard answers a question that was already waiting. A Claude Code hook — a script the CLI shells out to at a named moment in a turn — calls this server and then refuses to return, parking the turn on an open HTTP response; your phone reads what the hook registered, you tap, and that tap resolves the held response. Three files do that, and they share one shape: a Map of session id to an entry whose most important field is an injected resolve function, at most one entry per session, and a single settle funnel every exit runs through — plus a reaper, because nothing else will ever come along to release a hold.

spawn.ts inverts all of it. There is no hook, no parked turn, no held response. The dashboard is the one initiating, and what it creates is an operating-system process it immediately stops owning. So every piece of that shared machine is gone: nothing to resolve, nothing to funnel, and — the part worth watching — no reaper either.

What replaces them is a different problem. You spawned a detached child in another directory and returned instantly. Did it become a real session? The only honest answer lives on disk, in a transcript this server merely reads. Most of this lesson is about the three seconds before that answer exists.

Section 1 · Untrusted text, meet a flag parser

The prompt is never an argv element

The prompt a user types is the most obviously hostile input this feature handles, and the module's own doc comment states the rule it never breaks:

// spawn.ts:25-29 (compacted here)
//  - The prompt is never an argv element. `claude -p` parses argv the way
//    almost every CLI does: a value starting with `-`/`--` is read as a flag,
//    not as data, regardless of what flag it happens to follow. A prompt is
//    untrusted free text a user typed — `--dangerously-skip-permissions` is a
//    perfectly ordinary-looking sentence to start a prompt with

Read that middle clause carefully: regardless of what flag it happens to follow. Passing the prompt as the value of some flag does not protect it — the parser sees a token that starts with dashes and treats it as the next option, not as the previous one's value.

So the prompt goes somewhere the flag parser never looks. launch writes it to the child's stdin and closes the stream:

// spawn.ts:458-459
child.stdin?.write(input.prompt);
child.stdin?.end();

The obvious alternative — append the prompt to argv, quote it carefully — fails because there is nothing to quote against. Quoting is a shell concept, and no shell is involved.

The cost is a stream to manage rather than a string to pass, and a stream is an error surface of its own. Section 3 is where that bill arrives.

Array-form spawn, and never a shell

The second half of the same rule concerns how the child is started at all:

// spawn.ts:33-36 (compacted here)
//  - `child_process.spawn` is always called in array form, never with
//    `shell: true`. `shell: true` hands the whole command line to `/bin/sh`,
//    which re-tokenizes it — the exact step that turns a value into code if
//    it contains a quote, `;`, `$(...)`, or a stray space.

The actual call keeps that promise, and the option that would break it is simply absent:

// spawn.ts:442
child = doSpawn(config.claudeBin, args, { cwd: ref.path, env, detached: true, stdio: ['pipe', 'ignore', 'pipe'] });

shell: true is genuinely tempting: it is what lets you write cd dir && claude …, expand a ~, or glob a path. Every one of those conveniences is the same mechanism — a second parse of the command line by /bin/sh — and that second parse is exactly what turns data into code.

The trade-off is that everything the shell would have done must now be done in Node explicitly. That is why the working directory arrives as the cwd option rather than a cd, and why the environment is built as an object a few lines earlier instead of being inherited through a shell invocation.

A name that cannot look like a flag

The optional display name is an argv element — it rides in as the value of -n — so it gets a charset of its own:

// spawn.ts:87
const NAME_RE = /^[A-Za-z0-9][A-Za-z0-9 ._-]*$/;

Note that the first character is constrained separately from the rest. The comment above it says why, and it is a bug report rather than a hypothetical:

// spawn.ts:77-81 (compacted here)
//  - **The leading character is constrained separately** so a name can never
//    itself *look* like a flag: `-p` passed the old charset and became the
//    value of `-n`. No escalation was possible even then (a name is always
//    exactly one argv element, pinned by test), but the worst case — a name
//    the CLI's own option parser chokes on — is not worth keeping

The naive position here would be "argv safety already covers it, so skip the charset" — and strictly, for escalation, that is true. The comment concedes as much. The name is sanitized anyway because it also flows into the UI and later onto disk, so it earns validation on its own merits rather than borrowing argv's.

What it costs: a perfectly reasonable name containing /, :, or an emoji is silently dropped to undefined rather than reported. The dot is allowed only because that silence had already eaten v1.2 release once.

A user's prompt begins with the literal text --dangerously-skip-permissions is a flag I should never use. What keeps the CLI from reading that first token as an actual flag?

Nothing rewrites the prompt's content. parseSpawnRequest only trims it and length-caps it (spawn.ts:159-165); the text the child receives is byte-for-byte what the user typed.

There is nothing to quote against. Argv elements are handed to the child directly with no shell in between, so quoting has no meaning at this boundary — and the flag parser would still see the leading dashes.

Correct. launch writes it to child.stdin and ends the stream (spawn.ts:458-459). The CLI's option parser reads argv, never stdin, so no value there can be mistaken for a flag.

Array-form spawn does avoid /bin/sh, and that genuinely matters — but against a different attack. Removing the shell changes nothing about the CLI's own option parser, which would still read a leading -- element as a flag.

Section 2 · Validation

A ladder where malformed means lower

Permission mode is the one field where getting validation wrong is a privilege escalation, so it is not validated — it is clamped:

// spawn.ts:52-53, 102-103
/** The permission ladder, lowest to highest. Array index order IS the ordering. */
export const PERMISSION_MODES = ['plan', 'acceptEdits', 'auto', 'bypassPermissions'] as const;

export function clampPermission(requested: unknown, ceiling: unknown): PermissionMode {
  return PERMISSION_MODES[Math.min(modeIndex(requested), modeIndex(ceiling))];

The result is never higher on the ladder than the server-configured ceiling, and an unrecognized value on either side — including undefined — resolves to 'auto' rather than to the top. A malformed input can only ever make the outcome less permissive.

Two alternatives are worse in opposite directions. Throwing on an unknown mode turns a client typo into a dead launch button. Defaulting an unknown mode to the top of the ladder turns the same typo into bypassPermissions — the failure you least want to reach by accident.

The accepted cost is real, though: a client sending a mode this server has never heard of gets 'auto' silently, with no error to debug against. And "array index order IS the ordering" means reordering that one array is a semantic change, not a cosmetic one.

Only the prompt is allowed to refuse

Every other field in the request fails soft. An unrecognized model, effort, or name is dropped to undefined; a permissionMode outside the enum is clamped; only the prompt can reject the request outright:

// spawn.ts:156-165, 168-176 (compacted here)
if (typeof b.prompt !== 'string') return { ok: false, error: 'prompt is required' };
const prompt = b.prompt.trim();
if (prompt === '') return { ok: false, error: 'prompt must not be empty' };
if (prompt.length > PROMPT_CAP) return { ok: false, error: `prompt must be at most …` };

const model = typeof b.model === 'string' && MODELS.includes(b.model) ? b.model : undefined;

The reason is version skew. The dashboard and this server are deployed together but not always reloaded together, and a phone can hold a stale tab open for days. Strict validation that rejected any unknown field would make every version mismatch a broken launch button; drop-don't-reject means the rest of the request is still honored.

remoteControl shows the same instinct taken to its strictest form — b.remoteControl === true at spawn.ts:179, so absent, "yes" and 1 all fail soft to false.

The cost is silence in the one place you would want noise: a typo'd model name launches happily on the default model, and nothing anywhere says so.

The one field that refuses instead

resume breaks the drop-don't-reject rule on purpose, and the comment states the reasoning as a comparison of harms:

// spawn.ts:181-189 (compacted here)
// `resume` is the one optional field that REJECTS when present-but-malformed
// instead of dropping: silently ignoring it would launch a fresh session
// somewhere the user never asked for, which is worse than any 400.
if (b.resume !== undefined) {
  if (typeof b.resume !== 'string' || b.resume === '' || !RESUME_ID_RE.test(b.resume)) {
    return { ok: false, error: 'bad resume id' };

That is the whole test for whether a field may fail soft: what does the user get if it is ignored? A dropped model gives them the default model. A dropped resume id gives them a brand new session in a project they were only trying to continue.

Resume also changes argv's shape, and only its shape:

// spawn.ts:214-216
const args = input.resume
  ? ['-p', '--resume', input.sessionId, '--permission-mode', input.permissionMode]
  : ['-p', '--session-id', input.sessionId, '--permission-mode', input.permissionMode];

The CLI refuses --resume together with --session-id unless you also pass --fork-session, and forking is precisely what a resume must not do — plain --resume keeps the id and appends to the same transcript, which is what makes the dashboard row wake up. The cost: two argv shapes to keep in step, and no -n or --remote-control on a resume, since those combinations are unverified.

A request arrives with model: "opus-9" and resume: "not a valid id!". What does parseSpawnRequest return?

Dropping is right for model and wrong for resume. Resume is the single optional field that rejects when present-but-malformed (spawn.ts:187-190), exactly so a bad id can never quietly become a fresh session.

Correct. The unknown model fails soft to undefined, but a malformed resume returns { ok: false } and the launch never happens.

An unrecognized model never produces an error at all — it is dropped to undefined (spawn.ts:168-170) so a client running a different build can still launch with the rest of its request honored.

There is no ladder to clamp a session id onto — clamping is what permissionMode gets, because its values are ordered. A resume id either matches RESUME_ID_RE or the entire request is refused.

Section 3 · The launch

Register first, spawn second

The store entry is created before the process is, which looks backwards until you ask where a synchronous failure would otherwise be recorded:

// spawn.ts:422, 440-446 (compacted here)
entries.set(sessionId, entry);
…
let child: ChildProcess;
try {
  child = doSpawn(config.claudeBin, args, { … detached: true, stdio: ['pipe', 'ignore', 'pipe'] });
} catch (err) {
  fail(sessionId, undefined, errMessage(err));
  return sessionId;
}

A spawner that throws synchronously still has somewhere to write the reason, and the caller still gets an id it can poll for that reason. Spawn-then-register would leave that failure with nowhere to land: the POST returns an id nobody is tracking, and the UI has a row it can never explain.

The stdio triple is deliberate too — stdin piped because the prompt goes there, stdout ignored because nothing reads it, stderr piped because a failure's only explanation arrives on it. And detached: true with child.unref() at spawn.ts:497 is what lets the child outlive this server rather than dying with it.

The trade-off is an entry that can describe a process which never existed. That is why fail tolerates being called on an id that is already gone.

One environment variable, deleted on purpose

The child inherits this server's environment with a single key removed:

// spawn.ts:437-438
const env = { ...process.env };
delete env.CLAUDE_CODE_ENTRYPOINT;

That one deletion is load-bearing for the dashboard's own display. A server started from inside another Claude Code context — a desktop-app terminal, a Claude-driven shell — carries that marker in its environment, and a child that inherits it stamps claude-desktop into its transcript instead of sdk-cli. The scanner reads that stamp to decide a session's surface, so inheriting the variable costs the launched session its dashboard pill and its right to be resumed. The comment records both readings as measured on CLI 2.1.233, not inferred.

The tempting shorthand is env.CLAUDE_CODE_ENTRYPOINT = undefined. The comment rejects it precisely: this Node build happens to omit undefined-valued keys, but that is filtering behaviour to not lean on, whereas an absent key needs no guarantee from anyone.

The accepted trade-off is a denylist rather than an allowlist. Everything else the CLI needs — PATH, HOME, credentials — lives in that same environment, so passing only known-good keys would mean maintaining a list of the CLI's entire runtime dependency surface.

Four ways to fail, and the listener that saves the server

Failure can reach the store from four independent places — a synchronous throw from the spawner, the child's own 'error' event, an 'error' on the stdin/stderr streams, and a nonzero 'exit' — and all four route through one function, safe to call twice or after the entry is gone (spawn.ts:378).

The third of those is the one worth slowing down for:

// spawn.ts:455-457
child.stdin?.on('error', err => {
  fail(sessionId, undefined, errMessage(err));
});

A stream is its own EventEmitter. The handler on child does not cover it. Without this listener, an async EPIPE — the child dies, or never reads stdin, before the write finishes — throws unhandled and takes the entire dashboard server down. The comment records that as observed on Node 22, not theorised.

The naive version is one 'error' handler on the child, on the assumption that a parent covers its streams. It reads as complete and is the single most expensive omission available here: the failure mode is not a lost launch, it is a dead server.

The cost is four listeners per launch on an object this process has deliberately stopped owning.

More detail: why 'close' refines rather than replaces

Node may fire 'exit' before the child's stdio has finished draining, so the stderr tail can still grow afterwards. The 'close' handler therefore only refines the message with whatever arrived since. It cannot become the sole path: a spawn that never started at all fires no 'exit' and reaches 'close' with a synthetic negative libuv code, and refining on that would clobber the far better message the 'error' handler already set — which is why the guard at spawn.ts:490 checks all three of tail, non-null code, and positive code.

Why attach an 'error' listener to child.stdin when child already has one?

Nothing retries anywhere in this module. The handler's only action is fail(...) — the launch is recorded as failed, never attempted a second time.

That is a different listener: child.stderr.on('data') accumulates the tail. This one covers an error on the write side, which produces no stderr output at all.

detached governs process groups and lifetime — whether the child survives its parent — and has no bearing on which events reach which emitter. The child's own 'error' event fires exactly as it would otherwise; it simply never covered the stream in the first place.

Correct. child.stdin is a separate EventEmitter, so the child's handler does not cover it — and an async EPIPE with no listener throws unhandled, taking the whole process down.

A launched child exits cleanly with code 0 a few seconds in. What does the store record?

The exit handler returns early on code === 0 (spawn.ts:472), so nothing is ever marked failed. A clean exit is not a failure to report.

Correct. A fast run can finish before the next scan ever sees it, and the transcript, not the exit, is what matters then (spawn.ts:469-471).

The exit handler only ever calls fail; it never deletes. Entries leave the store through adoptLaunched, a TTL evaluated inside listLaunching, or stopLaunch.

That handler guards on code <= 0, so a zero exit is excluded there too — the same clean-exit rule — and it only ever refines a message some earlier failure had already set.

The child is running and unowned. What remains on this side is a small RAM-only store — and the most instructive thing about it is a piece of machinery the other three write paths all needed and this one does not.

Section 4 · The store

A store defined by what it refuses to be

The store's doc comment opens with a charter, and the second sentence is a refusal:

// spawn.ts:283-288 (compacted here)
// RAM-only store of launches still being watched. Charter: explain the first
// ~3 seconds of a launch, and report ones that never became a real session.
// This is NOT a session registry — the transcript stays the single source of
// truth … A launch that succeeds leaves no trace here once `adoptLaunched`
// sees its id; a restart drops every entry, live children included.

That scope is what keeps the dashboard honest about its own architecture. The whole app is a reader of transcripts on disk; a store that remembered live sessions would become a second, competing source of truth, and the two would drift the first time a session ended in a way nobody anticipated.

The alternative a beginner reaches for is exactly that second registry — track every session you launched, because you know about them. It works until a restart, at which point your registry is empty and the sessions are still running, and now the UI disagrees with reality with no way to tell which side is wrong.

The accepted cost is stated plainly in the comment: a restart drops every entry, live children included. A launch in flight across a server restart becomes invisible — until the scanner finds its transcript, which is the only claim this design was ever making.

No reaper, because someone is already looking

Here is the direct contrast with the other three paths, in the code's own words:

// spawn.ts:503-506
// Expiry is evaluated lazily here rather than on a timer: `pending.ts`/
// `plans.ts`/`messages.ts` each need a reaper because nothing else would ever
// read their entries, but the dashboard already polls every 3s, so the next
// `listLaunching` call is strictly simpler and cannot hold the process open.

Expiry is a side effect of being read. Both TTLs are checked inside the loop that builds the response, and an expired entry is deleted on the way past:

// spawn.ts:513-521 (compacted here)
for (const [id, entry] of entries) {
  if (entry.state === 'launching' && now - entry.startedAtMs > LAUNCH_TTL_MS) {
    entries.delete(id);
    continue;
  }
  if (entry.state === 'failed' && now - (entry.failedAtMs ?? entry.startedAtMs) > FAIL_TTL_MS) {

A setInterval would work — it is what messages.ts does — but it brings machinery this store has no use for: create it on the first entry, clear it on the last, unref it so it cannot hold the process open. All of that exists to serve a reader that never comes, and here a reader comes every three seconds.

The cost is that expiry only happens when someone looks: a store nobody polls holds stale entries for the process's lifetime. Note also that now is a parameter rather than read internally, so a test can simulate elapsed time without faking the clock.

A rail against accidents, not attackers

MAX_LAUNCHING caps in-flight launches at four, and the comment is unusually careful to say what kind of limit it is not:

// spawn.ts:341-350 (compacted here)
//  - **`'launching'` only.** A `failed` entry lingers for `FAIL_TTL_MS`
//    (5 minutes) purely so the UI can explain itself, and it holds no process
//    at all — letting it hold a slot would lock a user out of launching for
//    five minutes after four transient failures, with a 429 that explains nothing.
//  - **The pre-adoption window only** (~3s, until `adoptLaunched` sees the id
//    on disk). It therefore bounds **rapid-fire POSTs**, not the number of live
//    sessions — ten launches a minute apart all succeed

It is not a security boundary, and the comment says why it cannot be: a caller with launch rights can simply prompt one session into spawning more. What it stops is a mistake — a retry loop, a flaky phone connection, a double-tap that beats React's re-render — from becoming four real claude processes on the account's quota. The handler enforces it at api.ts:856-857, filtering to 'launching' before answering 429.

Capping live sessions instead would need the session registry the previous card explained this store is deliberately not.

So the honest trade-off: no protection whatsoever against deliberate abuse, and a limit that is invisible to anyone who spaces their launches out — which is the entire population of non-accidents.

You launch ten sessions, one per minute, with MAX_LAUNCHING at 4. How many are refused with a 429?

This is what you would get if the rail counted sessions. It counts entries still in the launching state, and each of those has already left the store long before the next POST arrives a minute later.

The arithmetic is inverted — the first four are the ones that succeed, not the ones refused. And with a full minute between POSTs, no slot is ever occupied when the next one lands.

Correct. The rail bounds only the ~3-second pre-adoption window, so each launch has left the store before the next arrives — it limits rapid-fire POSTs, not live sessions.

A failed entry deliberately holds no slot: it lingers for FAIL_TTL_MS only so the UI can explain itself, and counting it would lock the user out for five minutes (spawn.ts:341-345).

Section 4 → Section 5

One question is still open, and it is the one the whole feature turns on: how does a store that refuses to be a session registry ever learn that a launch worked? The answer is that it does not — it is told.

Section 5 · Adoption

The scanner is the witness

The store never looks at the filesystem. The sessions handler, which has just scanned it, hands over the ids it saw:

// api.ts:141-146 (compacted here)
// Adopt before listing: a launch id that just showed up in `sessions` must
// not also be reported as still `launching` in the same poll.
adoptLaunched(data.sessions.map(s => s.id));
data.launching = listLaunching();

A launch that became a real session leaves no trace: its id appears in a scan, the entry is deleted, and from then on it is an ordinary row like any other. Note the ordering the comment insists on — adopt first, then list, so a single poll can never show the same session twice in two different states.

The alternative is to have launch watch for the transcript itself — an fs.watch, or its own poll. That duplicates the scanner inside the store and gives the store filesystem knowledge its charter says it should not have.

The cost is a dependency on being called correctly: an entry lingers until its TTL if a caller ever passes an incomplete id list.

The witness that proves nothing

Adoption has one exception, and it is the case where the evidence is worthless:

// spawn.ts:535-540
// A resume entry's id names a transcript that already exists, so seeing it
// in a scan proves nothing — deleting it here would swallow a failure
// before the user's next poll could ever render it. Resume entries leave
// via the TTLs in `listLaunching`, `stopLaunch`, or a failure instead.
const entry = entries.get(id);
if (entry && !entry.resume && entries.delete(id)) n++;

For a fresh launch, "this id is on disk" means the CLI got far enough to write a transcript. For a resume, the transcript was there before the launch existed — that is what makes it a resume. So the same observation carries information in one case and none in the other, and the resume flag on the entry exists to tell them apart.

Treating both alike is the natural mistake and it fails silently in the worst direction: the row vanishes on the very first poll, so a resume that died on startup is indistinguishable from one that worked.

The trade-off runs the other way instead. A resume that succeeds sits in the launching list for the full LAUNCH_TTL_MS — sixty seconds — even though it is fine, so the UI briefly shows a launching row for a session that is already running. A stale-looking row is cheaper than a swallowed failure.

Stopping is a deletion, not a state

The last operation signals the child and removes the entry in the same breath:

// spawn.ts:559-564
export function stopLaunch(id: string): boolean {
  const entry = entries.get(id);
  if (!entry || entry.state !== 'launching' || !entry.child) return false;
  entry.child.kill('SIGTERM');
  entries.delete(id);
  return true;

Leaving the entry in place would let the eventual exit mark it failed, and it would then sit in the list for five minutes labelled as a crash the user never hit — because they stopped it themselves. The two-state union ('launching' | 'failed') has no way to say "you stopped this" separately from "it broke".

Widening that union to a third state is the obvious fix and the comment declines it: the type is a shared contract the handler and the client already consume, so a new state ripples outward for one row's phrasing.

The cost is that the entry is gone before the child is: SIGTERM is a request, not a guarantee, and the store has kept no record to correct if the child ignores it. The later exit finds nothing and no-ops through fail's presence guard — the same path any exit takes after adoption.

Why does adoptLaunched skip an entry whose resume flag is set?

It does show up — --resume keeps the id and appends to the same transcript, which is exactly why the scan finds it. Appearing is what makes the check useless here, not what makes it work.

stopLaunch is one of the three exits available to a resume entry, alongside a TTL and a failure, but it only ever fires when the user asks for it. Nothing about being a resume routes an entry's removal through that function.

Correct. The id was on disk before this launch existed, so seeing it says nothing about whether the run started — and deleting on the first poll would swallow a failure before the user could see it.

The row's id is stable either way — that is why a resume reuses the existing id instead of minting one. What deletion would break is failure reporting, not identity.
