Mental model

Three ways to write into a session that only ever reads

This dashboard is a reader. It tails transcript files off disk and shows you what your Claude Code sessions are doing; it has no daemon, no socket into the CLI, no privileged channel. So how does a button on your phone put an answer into a session running in a terminal three rooms away?

The answer is that it doesn't, quite. A Claude Code hook — a script the CLI shells out to at a named moment in a turn — calls into this server and then simply refuses to return. The turn is now parked on an open HTTP response. Your phone reads what the hook registered, you tap, and that tap resolves the held response; the hook finally answers the CLI, and the session moves. The dashboard never pushed anything. It answered a question that was already waiting.

Three files implement that trick — pending.ts, plans.ts, messages.ts — and they are near-identical by design. Once you see the shared shape, each one collapses into "the same machine, bent around a different constraint the CLI imposed." A fourth path, spawn.ts, inverts the whole thing; it gets its own lesson.

Section 1 · The shared shape

A store that holds a promise, not a request

Each store keeps one Map of session id to an entry, and the entry's most important field is not data at all — it is a function:

// pending.ts:51-58 (compacted here)
interface Entry {
  timer: NodeJS.Timeout;
  resolve: (r: WaitResult) => void;
}

The HTTP handler creates the held response and passes resolve in. The store never imports an HTTP type, never sees a socket, never knows a browser exists. It is a state machine over promises that some caller happens to have attached to a response.

The obvious alternative is to let the store own the response object and call res.end() itself. That works, and it is how most people would write it first — but then every test of "does a superseded question release its waiter?" needs a fake request, a fake response, and a fake socket. The file's own header says the injection is "what makes the whole state machine unit-testable."

The trade-off they accepted: the store cannot clean up after a dead peer on its own, because it cannot see the socket close. Something outside has to notice and call cancel — which is exactly why that function exists.

One entry per session, and a newer one wins

Every store keys by session id and holds at most one entry. A second registration for a session that already has one does not error and does not queue — it supersedes:

// pending.ts:173-183 (compacted here)
// An existing entry for the session is superseded — its waiter is
// released with `superseded` and falls back to the terminal dialog.
if (prev) settle(prev, { status: 'superseded' });

Why not a queue? Because the thing being modelled has no queue. The CLI has exactly one question open at a time; a second registration means the first one is already gone — the tool call was denied and the model re-asked. Queueing would faithfully preserve a state the real system cannot be in, and the phone would answer a question the session stopped caring about minutes ago.

Superseding also self-heals. A re-asked question after a deny silently replaces the stale entry instead of colliding with it, so the failure mode is "the terminal dialog handles it" rather than "the store is wedged."

What it costs: an answer in flight from your phone can lose a race it cannot see, and the tap lands on an entry that no longer exists. That is what the mismatch check is for.

Every exit runs through one funnel

Answered, dismissed, superseded, expired, cancelled — every terminal transition goes through the same four lines:

// pending.ts:158-163
/** Finish an entry: fire `resolve` once, clear its timer, drop it from the map. */
function settle(entry: Entry, result: WaitResult): void {
  clearTimeout(entry.timer);
  if (entries.get(entry.sessionId) === entry) entries.delete(entry.sessionId);
  entry.resolve(result);
}

Note the identity check before the delete. It is not the session id that must match — it is the entry object. A late timer firing for an entry that was already replaced must not evict its replacement.

The naive version — deleting by session id, or letting each call site resolve its own promise — leaks waiters: a path that forgets to resolve parks a turn forever, and there is no daemon to notice. Funnelling every exit means "fires at most once" is a property of one function you can read in full, not a discipline spread across nine call sites.

More detail: why the timer is called the guaranteed reaper

The expiry timer is not a convenience — it is the only thing that bounds a hold. If the browser never answers, if the phone loses signal mid-tap, if the tab is closed: the timer fires, settle runs, the hook falls back to the terminal dialog. An answer arriving after it finds nothing and gets a 404, which the module header names as the stale-answer guard.

Two browser tabs are open on the same session and both tap an answer at almost the same instant. What does the second tap get, and why?

This would be the behaviour if answering merely wrote a field onto the entry. But answering calls settle, which deletes the entry as part of finishing it — after the first tap there is no entry left for a second write to land on.

There is no lock anywhere in these stores, and deliberately so. The comment on answer spells out the reasoning: Node is single-threaded, so the interleaving a lock would protect against cannot occur in the first place.

Correct. answer is synchronous by design: the first tap runs to completion, and settle has already removed the entry by the time the second is handled, so its lookup misses and returns not-found.

Nothing in these stores queues. One entry exists per session and a terminal transition removes it; there is no pending-answer list for a second submission to wait in, only the entry that is now gone.

Section 2 · pending.ts

Answering a question you are not allowed to answer

Here is the constraint everything in this file bends around: no hook can supply an answer to AskUserQuestion. The hook API has no "here is the user's choice" channel. What it has is the ability to deny a tool call with a reason string.

So the answer travels as a rejection. The module header states it plainly:

// pending.ts:5-8 (compacted here)
// the answer resolves the held response — the hook then denies the tool
// call with a reason naming the choice, which is the only supported way
// to get an answer into a live session.

The model asked a question, the tool call was denied, and the denial reason says "the user picked Rewrite the parser." The model reads that and proceeds as though it had been told — because it has been.

The alternative a beginner would reach for is to write the answer into the transcript file directly, or to fake a tool result. Both desynchronise the CLI from its own state: the transcript is a record, not an inbox, and the CLI's in-memory turn would still be waiting on a tool call nobody completed.

The cost of using the deny channel is that the answer arrives as an interruption rather than a return value, and the prose has to do the work of sounding like an answer.

Untrusted input, twice over

The question text arrives from the hook's stdin, and the answer arrives from a browser that may be on the open internet. Both are treated as hostile. sanitizeQuestions caps the number of questions, the number of options, and the length of every string, and drops anything malformed rather than throwing:

// pending.ts:80-90 (compacted here)

  for (const raw of input.questions) {

    const question = str(q.question, QUESTION_CAP);
    if (!question) continue;

Returning an empty array is not a silent failure — it is a signal. The header explains that an empty result tells the caller to reject the registration, which makes the hook fall back to the terminal dialog. The session is never worse off than if the dashboard did not exist.

Throwing would have been simpler to write. But a throw inside a hook-facing path turns a malformed payload into a stalled turn, and the whole design rule here is that every failure direction ends at the terminal dialog rather than at a hung session.

The nonce that stops a stale tab

Registration returns a questionId, and any answer must echo it back. If it does not match the entry currently in the map, the answer is refused with mismatch before validation even runs.

This is the counterpart to superseding. A tab left open on your desk is showing a question that has since been denied, re-asked, and replaced by a new entry with a new id. Without the nonce, that stale tab's answer would apply to whatever question happens to be open now — which is worse than not answering at all, because the model would receive a confident answer to a question the user never saw.

The same pattern appears in cancel: a late socket-close for a stale questionId is a no-op, so a dying peer cannot evict the entry that replaced it.

What it costs: every client has to carry and echo the id, and every answer path grows a branch. That is three extra lines in exchange for making the entire class of wrong-question-answered bugs unrepresentable.

Why does sanitizeQuestions return an empty array on a malformed payload instead of throwing?

An exception inside a request handler does not take the process down; it becomes a failed response. The reason for the empty array is about where the session ends up, not about protecting the process from a crash.

Correct. The empty array is a signal, not a swallowed error: it makes the hook decline to register, so the question falls back to the terminal dialog and the session continues normally.

TypeScript models throwing functions without difficulty, and several paths in this codebase do throw. The choice here is a deliberate failure-direction decision rather than anything the type system forced.

Adding a try/catch at the call site would be trivial if that were the obstacle. The point is what happens to the parked turn afterwards, which a caught exception still leaves unresolved.

Section 3 · plans.ts

The verdict the engine refuses to accept

plans.ts is pending.ts with one capability deliberately missing: you can send a plan back for revision from your phone, but you can never approve one. That is not caution — it is the CLI's own rule. ExitPlanMode is a tool the engine marks as requiring user interaction, and for such tools the CLI discards a hook's bare allow. Approval only counts when it happens on the plan card itself.

So the store's verdict union has exactly two members, and anything else is malformed:

// plans.ts:144-148 (compacted here)
if (req.verdict === 'dismiss') {
  settle(entry, { status: 'dismissed' });
  return 'ok';
}
if (req.verdict !== 'reject') return 'malformed';

The alternative — shipping an Approve button that calls allow anyway — would have produced the worst possible artifact: a control that looks like it works, returns 200, and silently does nothing, leaving the session parked while the user believes they released it. Refusing to build the button is the honest encoding of an engine constraint.

The accepted cost is a genuinely asymmetric remote: away from your desk you can redirect work but never green-light it.

Feedback is mandatory, and it is the payload

A reject with an empty feedback string is rejected as malformed — the store will not let you send a bare "no":

// plans.ts:151-154 (compacted here)
// Feedback is the whole point of a remote reject: without it the model has
// nothing to revise against, and a bare "no" is better said on the card.
const feedback = typeof req.feedback === 'string' ? req.feedback.slice(0, FEEDBACK_CAP) : '';
if (!feedback.trim()) return 'malformed';

The feedback then becomes the deny message the model reads, wrapped in prose that also tells it what to do next: revise, call ExitPlanMode again, stay in plan mode, do not start implementing.

That wrapper is doing real work. A denied ExitPlanMode with no instructions is a dead end — the model knows it was refused but not that it should try again, so it may abandon planning entirely or start coding. The CLI's own rejection path tells the model to revise; the hook has to reproduce that instruction itself, because it has replaced that path.

What it costs: the exact prose is now load-bearing behaviour, coupled to how the model responds — and prose has no type checker.

Why is there no Approve button in the plan panel?

A reasonable guess, and it would be a policy choice the team could revisit. The real reason is not a judgement call at all — the capability is refused upstream, so there is nothing here to decide.

It reaches the model on every reject: the feedback travels as the deny message the model reads. The channel exists and works; it is specifically the approving verdict that does not survive.

This reads like an unfinished feature but it is a closed decision. Building it would produce a button that returns success and changes nothing, which is why the verdict union has only two members by design.

Correct. ExitPlanMode requires user interaction, and for such tools the engine drops a hook's allow — the approval card is the only surface that can approve, so a remote Approve could never work.

Section 4 · messages.ts

Holding open a turn that already ended

The other two paths intercept a tool call mid-turn. This one fires on Stop — the moment the model has finished and is about to hand control back to you. The hook blocks that stop, which reopens the turn and lets a message typed on your phone become the session's next user message.

The reason text carries both the message and a set of away-mode instructions, and the comment explains why they have to ride along here:

// messages.ts:44-47 (compacted here)
// carry the away-mode instructions — `UserPromptSubmit` hooks (the
// remote-decision injection) do NOT fire on hook-continued turns, so this
// is the only place the reminder can ride.

The obvious alternative is a second hook on UserPromptSubmit to inject that context. It does not fire on a turn continued by a hook, so the instructions would silently vanish exactly when they are needed. Bundling them into the one reason string is the only delivery that survives.

The cost is a piece of prose duplicated in two places: the chat reader mirrors this exact wording to unwrap the record back into a normal-looking drawer message. Edit one without the other and a test fails — which the comment notes is the point, since it fails closed.

The sweep that has to exist here and nowhere else

The other stores get released by the world: a superseding registration, a tool result, a closing socket. A stopped turn produces none of those — nothing further happens in that session by definition, so nothing will arrive to release the hold. Left alone, every finished turn would sit parked until its deadline expired.

So this store runs its own reaper, and the release condition is not about the session at all — it is about you:

// messages.ts:189-196 (compacted here)
export function sweepIdle(): number {
  const thresholdSecs = getSettings().idleSecs;
  if (thresholdSecs === 0) return 0;
  const idle = (idleReader ?? readIdleSecs)();
  if (idle === null || idle >= thresholdSecs) return 0;
  for (const entry of waiting) settle(entry, { status: 'released' });

If your machine reports recent input, you are back at the keyboard, and holding the turn open for a phone reply is pointless — so every hold is released at once.

Read the guard conditions as failure directions. Unreadable idle time, on Docker or non-macOS, returns null and releases nothing, leaving the deadline timer as the reaper of last resort. Never releasing is a delay; releasing wrongly would cut short a window you were about to use.

More detail: the reaper only exists while holds do

The 5-second interval is created on the first hold and cleared when the last one goes, and it is unref()'d so it cannot keep the process alive. An idle server never spawns the ioreg subprocess that reads idle time — the cost is paid only while someone is actually waiting.

The idle reader cannot read idle time (you are on Linux, say) and returns null. What happens to a hold that is currently open?

This is the opposite of the chosen direction. Releasing on an unreadable signal would close reply windows on every machine that cannot report idle time, which is precisely the outcome the guard avoids.

Correct. A null reading makes sweepIdle return without releasing anything, so the hold stands and its expiry timer remains the reaper of last resort — the documented fail direction.

The interval keeps running as long as any hold exists; it clears only when the last entry is gone. An unreadable reading affects one sweep's outcome, not whether sweeps continue.

No such fallback is wired in here. Substituting a different signal would mean guessing at presence from session activity, and the code deliberately prefers doing nothing over inferring it.
