Important | bugs | client/src/hooks/useSessionChat.ts:94 | Chat tail polls can overlap. Two polls sent with the same `after=` cursor both append the same page, so messages show up twice in the drawer. | `setInterval(() => void poll(), refreshMs)` fires whether or not the last poll has finished, and refreshMs can be as low as 1000 (lib/settings.ts:172). `poll()` reads `cursor.current` (line 81), which only moves forward after the await (line 89), and then runs `setMessages(cur => cur.concat(page.messages))` (line 90). There is no in-flight or sequence guard. So if a chat fetch takes longer than refreshMs (a slow tailnet or phone link, or a large page), the second poll sends the same cursor and the same messages are appended again. useRoutines.ts guards against this with `createPollSeq`.

*Failure scenario:* phone on a slow tailnet link, chat drawer open with refresh at 1 s. One `after=<cursor>` fetch takes 1.4 s; the next tick fires with the same cursor; both resolve and `concat` the same page, so every new message renders twice until the drawer remounts. Merged: architecture Minor `useSessionChat.ts:79-94` (same poll, plus `loadOlder` has no `live` check so an older page can be prepended after a re-tail) and tests Minor `useSessionChat.ts:81` (no test imports the hook).

*Verification:* UPHELD — useSessionChat.ts:79-94 matches the claim: `setInterval(() => void poll(), refreshMs)` has no in-flight or sequence guard (the `busy` ref only covers `loadOlder`), `poll` reads `cursor.current` before the await and moves it only after (line 89), then appends without checking (line 90), and refreshMs can be 1000 (lib/settings.ts LIMITS). Nothing downstream removes duplicates: the server is stateless, and `readChatAfter` (server/lib/chat.ts:337) returns the same page for the same `after`. `serveSessionChat` (server/api.ts) is synchronous, and every request re-lists transcripts through `findTranscript`, so a response slower than refreshMs is plausible when the server is busy. ChatDrawer only runs `filterMessages` and keys rows by `m.uuid` (line 319), so a duplicate page shows twice (React only warns about the repeated keys). `loadOlder` (lines 104-118) also has no `live`/epoch check: if a re-tail happens while it is in flight (e.g. the chatFullText toggle re-keys `get`), it prepends the old page and overwrites `head.current`. Caveat: the duplicate bug only appears when a poll takes longer than refreshMs.

Important | security | server/lib/management.ts:438 | A cloned repo can expose any file on the machine to every unauthenticated LAN reader by shipping a symlinked `CLAUDE.md` or `.claude/settings*.json`. Membership checks run on the link path, but the read follows the link. | `memoryItems` checks `(await fsp.stat(p)).isFile()` and `readTextIfFile` (management.ts:74) also uses `stat`. Both follow symlinks, so a link that points at a regular file passes and its path joins the servable set (management.ts:797, via `settingsHooks`, which keeps a settings link only when its target parses as JSON). `readServableFile` (management.ts:816) then `stat`s and `readFile`s the target. A repo carrying `CLAUDE.md -> ../../../../.ssh/id_rsa` (or a settings link to `~/.claude/.credentials.json`) is served by `GET /api/configs/file` to any peer, because reads need no token. `readSkillFiles` (management.ts:116) and `readMdDir` already skip symlinks for exactly this reason; the memory and settings paths don't.

*Failure scenario:* user clones an untrusted repo containing `CLAUDE.md -> ../../../../.ssh/id_rsa` and runs `claude` in it once. The repo's cwd enters `listRecentProjects`, the link path joins the servable set, and any LAN peer can `GET /api/configs/file?path=<repo>/CLAUDE.md` with no token and receive the private key. Reads are open by design (remote-access.md), which is why the symlink check matters: the skill-dir reader already rejects symlinks; the memory and settings readers do not.

*Verification:* UPHELD — I could not refute it. `memoryItems` (management.ts:435-445) and `readTextIfFile`/`readJsonIfFile` (management.ts:72-90) use `fsp.stat`, which follows symlinks. `readProjectScope` (management.ts:508/510) runs them on `<cwd>/CLAUDE.md`, `<cwd>/.claude/CLAUDE.md` and `.claude/settings*.json`, so a link to a regular file is accepted (for settings, only if the target parses as JSON). `collectServablePaths` (management.ts:776-805) then adds the link path from `scope.memory`, `hook.declaredIn` and `s.exists`. It does this for every project `listRecentProjects` returns: any transcript cwd in the lookback window, plus pins. So the user only has to have run Claude in the cloned repo recently; no pin is needed. `serveConfigsFile` (api.ts:1690) checks only that the requested link path has no `..` and is in that set. `readServableFile` (management.ts:816-837) then `stat`s and `readFile`s the link, which follows it to the target. The guards don't help: `request-guard.ts` only checks the Host header and blocks cross-site writes, so a GET with no token passes. `server.listen(config.port)` (index.ts:503) gives no host, so it listens on every interface, LAN included. Only skill dirs reject symlinks, via `readSkillFiles` (`e.isSymbolicLink()` plus `lstat`, management.ts:116-134). The only symlink test (test/management.test.ts:627) covers skill dirs, not memory or settings.

## Refuted

Important | security | server/lib/management.ts:797 | `~/.claude/settings.json` and each project's `settings*.json` are served raw to unauthenticated LAN peers, including their `env` block. That undoes the secret redaction applied to MCP env values. | `collectServablePaths` adds every existing settings file (`if (s.exists) allowed.add(s.path)`), and `serveConfigsFile` (server/api.ts:1690) returns the full content with no gate. Meanwhile `normalizeMcpServers` (management.ts:314) cuts `env` down to key names, and management.ts:802 explicitly keeps files "that hold the env values the payload redacts" out of the set. A settings `env` entry like `GITHUB_TOKEN` or `ANTHROPIC_API_KEY` <REDACTED> is readable by anyone on the Wi-Fi with no token.

*Refutation:* The code is as described: settings*.json files go into the servable set (management.ts:796-798), and serveConfigsFile (api.ts:1690) returns them unredacted. But that is the documented, accepted design, not a bypass. docs/subsystems/remote-access.md:24 says "Reads stay open", only writes are gated (refuseWrite / ANSWER_TOKEN), and line 104 notes that every read endpoint, including full transcripts and chat history, is open to LAN peers. docs/subsystems/configs.md:37/61 lists global and project `settings*` as servable file content. The MCP env redaction covers a different store: ~/.claude.json and every .mcp.json stay unservable (management.ts:802, configs.md:150-152), and nothing serves those values. So no protected value leaks, and a peer that can read open transcripts gains no new access from settings.json.
