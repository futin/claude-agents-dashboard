## Important findings

Important | runtime | server/lib/archived.ts:190 | After every server start, the first GET /api/sessions poll blocks the event loop for about 5.6 s at this machine's scale. scan-snapshot.ts:104-105 calls archivedSessionIds() and desktopLiveSessionIds(), each of which sweeps the desktop app's whole record store and classifies every record into its own cache: classify at :190, classifyLive at :220. The two caches share no work, so each of the 1,646 records is opened and prefix-read twice. GET /api/pins, /api/configs and /api/git-stats take the same sync path through the same calls. | Measured read-only on this machine against ~/Library/Application Support/Claude/claude-code-sessions (1,646 local_*.json files, 227 MB): a cold process took 2,808 ms for archivedSessionIds and 2,850 ms for desktopLiveSessionIds; warm, the pair took 19 ms per poll. The cost premise in archived.ts:53 was measured on a 669-record store, and the store only grows, because a desktop-app "delete" is an archive.

**Failure scenario.** Restart the dashboard (`pnpm start`, or a crash and relaunch) with any tab open. That tab's next 3 s poll hits `GET /api/sessions`, and `scan-snapshot.ts:104-105` runs both desktop-store sweeps one after the other with sync `fs`. Every other request waits behind them: other tabs' polls, the hooks' `/wait` holds and any write. Warm polls then cost about 19 ms, so the stall comes back only on the next restart. It gets worse over time, because a desktop-app delete only archives a record, so the store keeps growing.

**Verification note (UPHELD).** `archivedSessionIds` and `desktopLiveSessionIds` (`archived.ts:177-236`) each run their own `listRecords` sweep and their own `readPrefix` through `classify` and `classifyLive`, into separate maps (`cache` / `liveCache`, :56/:59), all with sync `fs`. Both are called inside the async `serveSessions` handler (`api.ts:140`). The `listen` callback in `index.ts` warms neither one, so both start empty after every restart. The store holds 1,646 `local_*.json` files, 227 MB (1,586 `isArchived:false`, 52 true; counted 2026-11-25). At the per-record costs in `archived.ts:53` (measured on 669 records) that is seconds of sync work. The 2,808 + 2,850 ms figures are the auditor's own measurement, and the skeptic did not re-run them. One correction: `/api/pins`, `/api/configs` and `/api/git-stats` call only `archivedSessionIds` (api.ts:1456/1532/1542, git-stats.ts:527), not both.

Important | security | server/lib/request-guard.ts:51 | Setting `ALLOWED_HOSTS=*` turns off the DNS-rebinding guard. `.env.example:62` and `docs/subsystems/remote-access.md:131` offer `*` as an option for public tunnels. With it set, any public website the user visits can rebind its own name to 127.0.0.1 and have that request counted as loopback (`local`), which can write with no token. That is enough to run arbitrary commands, not just read data. | `hostAllowed` returns true for any Host when the rule is `*` (request-guard.ts:51). `rebindableHost` takes `local` away only for `*.local` and single-label names (origin.ts:181), so `Host: evil.example` on a loopback socket with no X-Forwarded-For resolves to `local` (origin.ts:161). `writeAccessFor` then returns `open` (api.ts:511). `crossSiteWrite` passes because the rebound page is same-origin (request-guard.ts:69). Scenario: the user sets `ALLOWED_HOSTS=*` for an ngrok tunnel. Later the user opens attacker.example, which rebinds itself to 127.0.0.1:4173. The page POSTs `/api/routines` with a `run: shell` job body, then POSTs `/api/routines/<name>/run` (api.ts:1943,2017). Those routine routes need only `isOwner()`, not the remote-answer switch. The page can also POST `/api/spawn` when remote answering is on. remote-access.md:128-131 describes the rebinding risk only as "read every open GET route" and never says that `*` also gives token-free writes and command execution.

**Failure scenario.** The user sets `ALLOWED_HOSTS=*` to get an ngrok or Cloudflare tunnel working, which is one of the options `.env.example:62` and `remote-access.md:131` list. Later the user opens a hostile page. That page rebinds its own hostname to 127.0.0.1 and POSTs same-origin to `/api/routines` with a `run: shell` job, then to `/api/routines/<name>/run`. The request arrives on a loopback socket with no `X-Forwarded-For`. The server treats it as the trusted local owner, so it needs no token and the command runs. #524 closed this hole for `.local` and single-label names, but `*` reopens it for every name.

**Verification note (UPHELD).** The skeptic traced the full chain. With `*`, `hostAllowed` accepts any Host (`request-guard.ts:51`). `rebindableHost` removes loopback trust only for `*.local` and single-label names (`origin.ts:181`), so `Host: evil.example` on loopback still resolves to `local` (`origin.ts:161`). `writeAccessFor` then returns `open` (`api.ts:511`). `crossSiteWrite` passes because the rebound page is same-origin (`request-guard.ts:69`). The listener runs only those two checks (`index.ts:222-225`). `config.ts:361` accepts `*` without a warning. Routine create and run gate only on `refuseWrite` plus the owner check. The docs cover the risk of `*` only for reads (`remote-access.md:128-131`). One limit: the hole is open only while the user has set `*`. `.env.example` recommends `.ngrok.app` instead, and the docs call `*` switching the check off. Neither the DNS rebinding nor the browser's Local Network Access behaviour was tested live.
