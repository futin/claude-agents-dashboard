## Important findings

Important | tests | server/lib/handover.ts:174 | The re-poll loop in `watchHandOver` is never run by any test. A change that ends the watch after one poll would stop every fresh desktop launch from reaching the desktop app, and the suite would still pass. | handover.test.ts calls `stepHandOver` by hand and never runs the timer. The only use of `watchedHandOvers` is spawn-endpoint.test.ts:612/663, which only checks that the id was registered. The first `stepHandOver` always returns 'wait' (the settle poll at handover.ts:148-150), so the `step === 'wait' && timers.has(id)` re-schedule is what makes the hand-over happen at all.

**Failure scenario:** a refactor of `watchHandOver` that stops re-scheduling after the first poll passes the whole suite. Every fresh desktop launch then stays headless and never opens in the desktop app, while the UI (SessionsView.tsx:197) has already promised that it will.

**Verification (UPHELD):** the real lines are handover.ts:67-81, with the re-schedule at :73 (the file has 92 lines; the auditor's :174 is wrong). Only line 73, `if (step === 'wait' && timers.has(id)) schedule()`, calls `stepHandOver` again, and the first sighting of a finished turn always returns `wait`. test/handover.test.ts imports only `stepHandOver`, `HANDOVER_MAX_MS` and `resetHandOvers`. spawn-endpoint.test.ts:612/:663 only check `watchedHandOvers()` straight after the request. Nothing references `HANDOVER_POLL_MS` or fake timers.
