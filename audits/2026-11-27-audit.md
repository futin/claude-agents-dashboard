## Important findings

Important | tests | server/api.ts:1167 | No test checks that `POST /api/spawn` refuses an untrusted caller. This is the route that starts a headless `claude` with a permission mode. No test sends it a LAN or bad-token request and checks for a 403 with nothing launched. The same is true of `POST /api/spawn/:id/stop` (:1388). If the `if (...) return` around the gate were dropped, a LAN peer could launch sessions and the suite would stay green. | test/spawn/spawn-endpoint.test.ts only checks 403 for `serveSessionStop` (:1025). Every `serveSpawn(cfg, …)` call there (:187, :236, :251, :275, :288) goes through the trusted loopback `post()` helper with no token or `X-Forwarded-For`. The only thing pinning the gate is test/guards/write-paths.test.ts:25, which matches the text `refuseWrite(config, req, res)`. That text still matches if the call stops gating, e.g. `refuseWrite(config, req, res);` with no early return.

**Failure scenario.** Someone refactors `serveSpawn` or `serveSpawnStop` and drops the `return` after `refuseWrite(config, req, res)`, or swaps the gate for a helper that answers 403 but lets the handler carry on. Every suite stays green: the endpoint tests call both handlers only as a trusted loopback peer, and the write-paths guard only checks that the `refuseWrite(config, req, res)` text is present. After that change, a LAN peer, or a tunnel caller with a bad token, can start a headless `claude` with any permission mode and stop any spawned session. This is the most powerful write route in the server.

**Verification note (UPHELD).** serveSpawn (server/api.ts:1168) and serveSpawnStop (:1388) both gate with `if (refuseWrite(config, req, res)) return;`, but no test sends either one an untrusted request. I searched the whole test/ tree. Every serveSpawn/serveSpawnStop call in test/spawn/spawn-endpoint.test.ts goes through the loopback post() helper with no headers. The only untrusted-caller test there, at :1025-1034, targets serveSessionStop. The LAN, X-Forwarded-For and bad-token tests elsewhere hit other routes: /api/remote-answer and /api/settings in api-write-trust, /api/remote-answer and /api/notify/test in api-reject-log, and only the sessions answer, plan-answer and message-answer routes in api-answer-endpoints. test/api/api-decode-path.test.ts sends POST /api/spawn/%ZZ/stop from loopback and only checks the 400 for bad path encoding. test/guards/write-paths.test.ts:25 only checks that the text `refuseWrite(config, req, res)` appears, which still matches with the early return removed.
