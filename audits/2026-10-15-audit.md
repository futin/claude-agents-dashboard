## Critical findings

Critical | bugs | server/index.ts:185 | One unauthenticated request whose path is `//`, `///` or `//%` kills the whole dashboard process. The request listener calls `new URL(req.url, 'http://local')` with no guard, and that call throws synchronously. | Node's HTTP parser hands `req.url === "//"` to the listener (checked with a raw-socket `GET // HTTP/1.1`). `new URL('//', 'http://local')` throws ERR_INVALID_URL. index.ts:147 says no `uncaughtException` handler exists, so the throw escapes the listener (the same failure class `decodePath` was added to stop). The server binds every interface.

*Found by both bugs shards (merged).* **Failure scenario:** anything on the LAN or tailnet sends `GET //%zz HTTP/1.1` to :4173 or :5174 (a scanner, a typo'd curl, a crawler), and the API process exits. Every held hook socket drops with it. The orchestrator watchdog's `POST /api/spawn`
recovery path goes too. **Fix:** wrap the `new URL` call (or the whole listener body) in try/catch and reply 400. **Verification:** UPHELD. The call is the unguarded first statement of the
listener. `node -e` on v22.23.1 throws for `//`, `//%zz` and `//[`, and `'//'` is truthy, so the `|| '/'` fallback does nothing. Nothing catches the throw: there is no try/catch in
`createRequestListener`, `http.createServer` does not catch listener throws, and the only process handler is `unhandledRejection` (line 76).

## Important findings

Important | architecture | client/src/hooks/usePersistedState.ts:10 | The answer-token auth path is copied into 12 places (11 hooks plus SettingsView.tsx:156). Each copy makes its own `usePersistedState('dashboard.answerToken')` call, and that hook has no cross-instance sync. So a token typed into one panel is not seen by the hooks mounted next to it. Concrete case in the chat drawer: MicButton's dictation gets a 403, the user enters the token in MessagePanel, and the next dictation (or a PlanPanel/ResumePanel send) is still sent with the old empty token. It keeps failing and re-asking for the token until the drawer remounts. | usePersistedState.ts:11-30 reads localStorage once at mount and only ever writes, with no storage-event or shared store. ChatDrawer.tsx:108-110 mounts usePendingQuestion, usePendingPlan and usePendingMessage, each with its own token state (usePendingMessage.ts:39, usePendingPlan.ts:41, usePendingQuestion.ts:43). MicButton (inside MessagePanel and ResumePanel) uses useDictation.ts:31, and ResumePanel uses useSpawn.ts:37. Each of MessagePanel.tsx:100, PlanPanel.tsx:206 and ResumePanel.tsx:69 calls only its own hook's setToken. The hazard is documented in useSpawn.ts:15-21 ("would not see this write until the panel remounted") and useStopSession.ts:20-22, but the fix was applied inside each hook and never across them. The Bearer header is also hand-built in useSpawn.ts:44, useDictation.ts:78, useStopSession.ts:40, useGitFetch.ts:38, useRemoteAnswer.ts:50, useOpenFolder.ts:31, useServerSettings.ts:69, usePins.ts:53 and :79, usePendingPlan.ts:94, usePendingMessage.ts:92 and usePendingQuestion.ts:100.

**Failure scenario:** with `ANSWER_TOKEN` set, a phone user hits a 403 on dictation and enters the token in the message panel. Dictation and plan answers in the same drawer keep 403ing until the drawer
is closed and reopened. **Fix:** one `useAnswerToken()` backed by a module store, or `useSyncExternalStore` over localStorage plus the `storage` event, and one `authHeaders()` helper. **Verification:**
UPHELD. The value is read once in a lazy init, with no listener or context. The `tokenRef` in the `usePending*` hooks mirrors only that hook's own copy. Correction: ResumePanel mounts conditionally, so it may
pick up the fresh value.

Important | architecture | server/lib/usage-ledger.ts:412-421 | The ledger's first "seeding" tick reads every transcript on the machine from byte 0, then throws away everything it parsed. This happens on every server start and every time recording is switched back on (`resetLedgerRecorder` at :501). | A new cursor starts at `offset: 0` (:414). `collectEvents` then does `Buffer.alloc(size - offset)` and `readSync` of the whole file (:418-421) and `JSON.parse`s every line. Then `recordLedgerTick` returns at :508 without using any of it ("seeding tick"). On this machine that is 4,111 `.jsonl` files, about 2.8 GB, the largest 23 MB, all read synchronously inside the usage fetch, which blocks the event loop. Seeding only needs `cursor.offset = size`. The :500 comment says reseeding is cheap, and docs/subsystems/usage-limits.md:756 does not mention this cost. Each later 60 s tick also stats every file twice: `statRef` inside `listUsageTranscripts` and `fs.statSync` again at :407.

**Failure scenario:** with usage recording on, every server restart blocks the event loop while it reads about 2.8 GB synchronously. Polls, held hook sockets and push all stall. **Fix:** on seeding, set
`cursor.offset = size` without reading. **Verification:** UPHELD, with a caveat: this only applies when the opt-in `recordUsageHistory` is on (`DEFAULT_RECORD_USAGE_HISTORY = false`, settings.ts:68). `cursors` is an in-memory Map that is never loaded from disk. `listTranscripts` has no lookback filter, and the seeding branch (:507-509) discards the parsed `events`.
The 4,111-file / 2.8 GB figure is the auditor's own measurement and was not re-measured here.

Important | fe-be | server/api.ts:1018 | POST /api/settings answers with a different shape from GET /api/settings. The client swaps its whole state for the POST reply, so the "restart to pick up .env changes" warning disappears after any setting is saved. | GET (api.ts:588) fills `staleEnvKeys: staleEnvKeys()`, but POST sends `{ ...next, notifyAvailable }` where `next` comes from setSettings, which returns getSettings() with a hard-coded `staleEnvKeys: []` (server/lib/settings.ts:249,301). useServerSettings.ts:78 calls `setState((await res.json()) as ServerSettings)`, and SettingsView.tsx:104/279 draws the warning from `server.state?.staleEnvKeys`. Scenario: edit NTFY_TOPIC in .env, open Settings and the warning shows; toggle any switch and the warning is gone, while pushes still go to the old topic.

**Fix:** build the POST reply the same way as GET (`staleEnvKeys: staleEnvKeys()`), ideally with `satisfies ServerSettings` on both (see the fe-be Minor at api.ts:1581). **Verification:** UPHELD. The client fetches GET only once, in its
mount effect, and never again after a save.

Important | tests | server/api.ts:1008 | The token gate on `POST /api/settings` (`serveSettingsWrite`) is untested. Every write route next to it has a no-bearer 403 test, but this one does not. | test/api-body.test.ts:117,134,146,158 all call `withEnvFile('', …)`, so `ANSWER_TOKEN` is empty and `tokenOk` always passes. Compare test/api-pins.test.ts:64 and test/api-wait-endpoints.test.ts:78, which do test the 403.

**Failure scenario:** if someone drops the `tokenOk` check from `serveSettingsWrite`, `pnpm test` stays green, and anyone on the LAN can turn off push or change the answer window. **Verification:** UPHELD. No
generic write-route loop includes `/api/settings`. api-reject-log covers only `/api/remote-answer` and `/api/notify/test`.

Important | bugs | server/lib/agents-cache.ts:89 | Once the cache holds 32 files, each new entry evicts itself as soon as it is inserted. After that, every `readAgentsCached` call for a new transcript re-reads the whole file on every 3s detail or scan poll. | `freshEntry()` sets `lastUsed: 0`, then `cache.set` and `evictIfNeeded()` run before line 97 sets `entry.lastUsed = Date.now()`. The eviction picks the smallest `lastUsed`, which is the new entry at 0. The rest of the call then works on an entry that is no longer in the map, so the cache stays fixed on the first 32 files the process saw.

**Failure scenario:** a long-running server has seen more than 32 transcripts. Opening any newer session's detail panel then re-reads that whole transcript every refresh tick. **Fix:** set `lastUsed = Date.now()` in
`freshEntry` (or before `evictIfNeeded`), and add a test that a 33rd insert survives. **Verification:** UPHELD. The strict `<` scan evicts the new key. Callers are `useSessionDetail`'s interval → `GET
/api/sessions/:id` (api.ts:218) and scan.ts:311 in the 3s list poll. The LRU test (agents-cache.test.ts:234) only checks that size ≤ 32, so it misses this.

Important | bugs | server/api.ts:1464 | After a resume fails, retrying it is refused with 409 `already resuming` for 5 minutes, even though nothing is running. | `listLaunching()` also returns `failed` entries, which it keeps for `FAIL_TTL_MS` (5 min, spawn.ts). The check `listLaunching().some(e => e.sessionId === rid)` does not filter on `state === 'launching'`, unlike the rate-limit check at api.ts:1407. docs/subsystems/spawn.md:188 says only a resume "already in flight" should get that reply.

**Fix:** add `&& e.state === 'launching'`, and add a test for a retry after a failure. **Verification:** UPHELD. `toPublic` keeps the `sessionId` on failed entries (spawn.ts:499), and nothing evicts them before the TTL.
The only test (spawn-endpoint.test.ts:353-362) covers the in-flight case.

Important | security | server/api.ts:501 | Any website the user visits can trigger the write routes when ANSWER_TOKEN is empty, which is the default (a CSRF hole). Nothing checks Origin or Sec-Fetch-Site, and request bodies are parsed as JSON whatever their Content-Type, so a cross-origin `no-cors` POST with `text/plain` goes straight through without a preflight | `tokenOk` returns true on `!config.answerToken`, and DEFAULTS.ANSWER_TOKEN is '' (server/lib/config.ts:132). `readJsonBody` (server/api.ts:345-349) calls `JSON.parse` without checking the content-type. With CLAUDE_BIN set, a malicious page that POSTs `/api/spawn` with `{project:<dirName>, prompt, permissionMode:'auto'}` starts a real `claude` session running the attacker's prompt, and the default SPAWN_MAX_PERMISSION is 'auto' (config.ts:144). With the defaults (REMOTE_ANSWER true) it can still POST to pins, settings, answer, plan-answer and message-answer. The documented posture (docs/subsystems/remote-access.md) only covers LAN and tailnet clients, not requests carried by the user's browser.

**Failure scenario:** the user browses any page while the dashboard runs with `CLAUDE_BIN` set and no token. The page fires a `fetch('http://localhost:4173/api/spawn', {method:'POST', mode:'no-cors', body})`,
and a `claude -p` session runs the attacker's prompt in `auto` mode. **Fix:** cheapest first. (a) Reject a POST whose `Sec-Fetch-Site` is `cross-site`, or whose `Origin` is present and not one of the
dashboard's own origins. (b) Require `Content-Type: application/json` on JSON routes, which forces a CORS preflight that the server never answers. Either one closes it without touching the LAN-trust model. **Verification:** UPHELD. Nothing in `server/`
reads Origin, Referer or Sec-Fetch-*, or sets CORS headers. The only content-type check is the audio check in transcribe (api.ts:412).

Important | security | server/index.ts:181 | The production server never checks the Host header, so DNS rebinding lets any website read the open read routes: full transcripts, `/api/configs/file` bodies and `/api/git-stats`. It also exposes the exact project dirNames the spawn CSRF above needs | `createRequestListener` dispatches every route without looking at `req.headers.host`. The Vite dev server keeps its Host guard, and docs/subsystems/remote-access.md:74 calls that guard a DNS-rebinding defence, but the :4173 prod listener has no equivalent.

**Fix:** allowlist the `Host` header in prod (localhost, LAN IPs, `*.ts.net`, plus an env-configurable extra list for tunnels), mirroring Vite's `allowedHosts`. **Verification:** UPHELD. No
`headers.host`, `headers.origin` or `x-forwarded-host` read exists anywhere in `server/`. remote-access.md names DNS rebinding only for the dev guard (73-79), so the prod gap is neither documented nor
accepted.
