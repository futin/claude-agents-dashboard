Important | security | server/lib/request-guard.ts:19 | The DNS-rebinding guard always accepts `*.local` names (line 19) and every single-label name (line 47). Those are exactly the names an attacker on the same LAN can answer, through mDNS for `.local` and LLMNR/NetBIOS for single-label names on the Windows browser side of WSL. So a LAN peer, which is meant to be read-only, can rebind a name to 127.0.0.1 and get a write from the user's own browser counted as loopback, which is trusted. | Scenario: a LAN attacker serves a page at `evil.local:4173` and gets the user to open it. It then re-announces `evil.local` as 127.0.0.1 and POSTs same-origin to `/api/spawn` (or `/api/routines` with `run: shell`, or `/api/settings`). `hostAllowed` passes because of the `.local` suffix (request-guard.ts:19,49). `crossSiteWrite` passes because `Sec-Fetch-Site` is `same-origin` (:72). The doc comment at request-guard.ts:16 justifies the exemption with ".local is mDNS (LAN-only)", but LAN peers are exactly the actors the write gate refuses. docs/subsystems/remote-access.md:123-125 lists the exemption but does not cover this attack. **Failure scenario:** A LAN peer serves a page at `evil.local:4173` and gets the user to open it. It then re-announces `evil.local` as 127.0.0.1 over mDNS and POSTs same-origin to `/api/spawn`. **Verification:** UPHELD — The code does what the claim says. `hostAllowed` (server/lib/request-guard.ts:47-48) passes any single-label name and any `*.local` name unconditionally. `crossSiteWrite` (:69) passes a `Sec-Fetch-Site: same-origin` POST. The listener runs only these two checks before routing (server/index.ts:222-225). A request on a loopback socket with no `X-Forwarded-For` header resolves to `local` (server/lib/origin.ts:143-145), and `writeAccessFor` returns `open` with no token (server/api.ts:508-509). So a name a LAN attacker can answer through mDNS or LLMNR, re-pointed at 127.0.0.1, gets token-free write access that the attacker's own LAN socket would be refused. That contradicts the guard's stated reason (".local is mDNS (LAN-only)"), since the LAN is the network the write gate treats as read-only. I did not test whether real resolvers accept a loopback answer or whether Chrome's Local Network Access checks block the request; these are the preconditions the claim already states, not gaps in the code reading.
